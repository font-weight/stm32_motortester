# USB-002: политика транспортных эпох

## Текущая черновая дельта PMAOVR — issue88

К сохранённой ниже исторической модели добавлена отдельная причина
MT_USB_EPOCH_PMA_OVERRUN (128), без изменения layout структуры и прежних битов.
Текущий token отравляется, io_failures увеличивается с насыщением; epoch не
меняется. Старый token не может отравить новый. Cleanup receipt, config, soft
resume или HELLO не снимают ошибку: нужен настоящий BUS_RESET, его обработка,
подтверждённый foreground Stop/cleanup, configuration и свежий HELLO.

Bridge ingress берёт существующий guard и меняет только metadata. Он не
вызывает Stop/CDC/controller в ISR и не зависит от свободного места в очереди.
В bridge-enabled FSDEV overlay наблюдаемый PMAOVR проверяется до CTR: fault
фиксируется, флаг очищается, обработчик возвращается. Данные, уже переданные
в PMA до обнаружения, отозвать нельзя; успешное новое окно из этих остатков
не заявляется. Здесь проверяется CDC-only профиль с передачами не более64 байт,
без поддержки произвольных FIFO/ISO/multi-packet путей.

При RESET и PMAOVR в одном снимке ISTR старый PMAOVR очищается вместе с RESET
до обычного reset event: оставшийся флаг не должен попасть в новую эпоху.
Это не синтетический reset. SOF остаётся перед reset/overrun, как в upstream;
текущий CDC-only профиль не имеет SOF class callback. Исходный vendor не меняется,
изменение — отдельный hash-pinned build overlay; без CFG_MT_USB_BRIDGE прежняя
ветвь сохранена.

Команда текущего unit-набора: `sh tests/usb-epoch/run.sh`. Его новые проверки
не подменяют интеграционный FSDEV/MMIO replay и независимый вердикт.
Исторические object SHA, размеры и supporting receipts ниже не переносятся
на изменённую реализацию. Старые global build/input/image pins намеренно
отвергают новую source/patch-композицию; их пересчёт требует отдельного
rebuild/review. Подмена hashes без проверки не выполняется. Полный стек,
физические PMA/IRQ races и аппаратная пригодность этой дельтой не подтверждены.

## Историческая база модели


Ограничения ниже описывают самостоятельный модуль исходной итерации. В единой композиции подключены `mt_usb_bridge`, layered USB005 core/fsdev patches и IRQ guard. Реальные USB/IRQ/timing и приёмка композиции остаются открытыми.

Черновик [задачи 54](https://github.com/font-weight/stm32_motortester/issues/54).
Модуль реализует только переходы метаданных. Он не подключён к TinyUSB, не
перехватывает reset/overflow и не исправляет наблюдавшиеся отрицательные
сценарии upstream. Изменений wire или host здесь нет.

## Зачем нужен номер эпохи

Операция получает ненулевой token при своём начале. Новый физический reset
или достоверный disconnect выдаёт другой token. Старый callback не может
получить разрешение только потому, что новое устройство уже ready.
Нельзя заново присвоить старой операции текущий token после прерывания.

Все обращения, включая чтение разрешения, сериализует вызывающий код.
Проверка token и защищаемая DCD-операция должны находиться в одной короткой
целевой критической секции. Здесь нет PRIMASK, C11 atomics или IRQ barriers.
Сам по себе успешный native-тест не доказывает корректную синхронизацию MCU.
Повторный init живого состояния запрещён, пока остаются старые tokens/events.

## Порядок нормального открытия

1. Producer реального BUS_RESET вызывает reset и сохраняет выданный token.
2. После настоящего enqueue передаёт enqueued(token, reset=1, accepted=1).
   При отказе передаёт accepted=0; эпоха блокируется до нового reset.
3. Foreground выполняет hard-quarantine/попытку Stop и отмечает cleaned.
   Эта отметка не подтверждает успешную физическую остановку. Неудача Stop
   сохраняется в контроллере; HELLO должен снова проверить аппаратный путь.
4. Только при разрешённом dispatch reset выполняется настоящий reset-handler.
   После его успешного завершения вызывается reset_done. Повторная обработка
   того же reset не разрешается.
5. Теперь допускается enumeration текущей эпохи, но ещё не прикладной обмен.
   Только после успешной конфигурации CDC и требуемой status-операции вызывается
   configured. Затем app_io разрешает прикладной путь.

Это вызовы внешнего для этого модуля bridge. Состояние
TinyUSB ready, открытые endpoints, здоровье TIME001 и политика DTR проверяются
интегратором дополнительно. Разрешение метаданных не заменяет эти проверки.

## Отказы и старые результаты

Неуспешный enqueue текущей эпохи, submission, completion или deconfiguration
защёлкивают запрет. Ни empty queue, ни повторная конфигурация, ни resume/HELLO
не снимают его. Нужен следующий реальный reset и весь порядок открытия.
Disconnect создаёт новую заблокированную эпоху; сам он reset не подтверждает.
Автоматический config0 → config1 без reset этой первой политикой не реализован
и остаётся открытым требованием полного lifecycle, не новым условием Windows.

Результаты с устаревшим token игнорируются и не портят новую эпоху. Caller
передаёт исход каждого реального enqueue/отказа ровно один раз; диагностика
считает уведомления, а не самостоятельно обнаруженные аппаратные события.
Диагностические счётчики насыщаются и не сбрасываются при очередном reset.
Повторное принятие уже обработанного reset не даёт разрешения dispatch заново.

Текущий hard counter доходит до UINT32_MAX, но не переходит через ноль.
Попытка выдать следующий token приводит к постоянному запрету; reinit нельзя
использовать как обход, пока старые tokens ещё существуют. Для восстановления
нужен полный контролируемый перезапуск всех владельцев/очередей, не этот API.

## Suspend и отложенные события

Suspend не меняет hard epoch. Он выдаёт отдельный serial: позднее подтверждение
старого suspend не снимет более новую паузу. Resume требует текущие epoch и
serial, реальное подтверждение возобновления и выполненные foreground-действия.
Метод сам не наблюдает USB-шину. Исчерпание soft serial блокирует текущую эпоху
до следующего физического reset; пара hard token + soft serial не повторяется.

Во время soft pause запрещены обычный dispatch, core I/O и app I/O. Текущие
события требуется **удерживать**, а не выбрасывать: иначе теряются completion
или принятые байты. Producer-метаданные resume проверяются до продолжения
очереди; нельзя зависнуть в ожидании resume callback за удержанными событиями.
Возврат dispatch=0 сам не различает defer, stale и poisoned. Эта классификация
и хранение событий относятся к внешнему queue bridge.

## Проверки и границы

Авторский набор строгого C11 и ASan/UBSan проверяет порядок reset/queue/cleanup,
config-before-reset, старые tokens, queue/submission failure, soft serial и
насыщение. Команда: sh tests/usb-epoch/run.sh. LeakSanitizer отключён; проверки
утечек не заявляются. Независимый supporting-набор выполнил 12 направленных
групп, модель коротких последовательностей и воспроизводимых длинных обходов:
2 628 485 переходов. Проверки strict C11 и ASan/UBSan прошли. Состояния около
исчерпания счётчиков заданы явно через тестовые поля, а не миллиардами реальных
reset. Десять небольших намеренных нарушений правил обнаружены направленными тестами.
Dot A отдельно воспроизвёл полный набор из копии; число переходов не является
оценкой качества или доказательством аппаратной безопасности.

ARM GCC 14.2.1, Cortex-M3/Thumb, -Os, -fno-short-enums: объект 470 байт text,
0 data/bss, состояние 48 байт; SHA-256 объекта
2b63118f5e871c51c6675a4203f18dbba7f0d16239dbd2715623c1ef90154159.
Единственная undefined-зависимость — memset. Независимый вариант с -O2 даёт
708 байт text при том же состоянии; разные флаги не смешиваются в бюджете.
Команда из корня: TC=/path/to/toolchain/usr sh tests/usb-epoch/arm-check.sh.
Это отдельные objects, не полный ELF и не максимальный стек программы.
Точные supporting-команды и ограничения: [замороженный набор](../../tests/usb-epoch/supporting/REPORT_RU.md).
Его runner воспроизведён из чистой копии tests/ и inputs/, без зависимости от
прежних исследовательских каталогов.

Патч queue envelope, SETUP accounting, фильтр/guard DCD-вызовов, target critical
section, физические reset-submission races и ограничение ADC <2560 мкс здесь
не реализованы. Исходные контрпримеры TinyUSB нельзя считать устранёнными этим
модулем. До применимого независимого заключения сохраняется draft.
