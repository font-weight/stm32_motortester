### Трассировка приёмки #42

1. Независимые 19 бинарных golden-векторов, точные поля ACK/CAPS/CONFIG, CRC и COBS;
   разбиения всех команд, coalesced input, побайтовый read и отсутствие выделения sequence/END при read(0).
2. Двадцать полных циклов неизменённого HOST-006: ARM → trigger → настоящие BEGIN/DATA/END bytes → STOP.
   Отдельно проверяются 2048 исходных кодов, длина 4096, порядок DATA и CRC.
   Отрицательный контроль с изменёнными допустимыми DATA-кодами показывает, что
   `WINDOW_END_ADMITTED` контроллера **не означает** успешную проверку массива.
3. RELEASE с правильными ID/CRC, точный повтор без исполнения, новый request с ACK без повторного rearm,
   неверные и устаревшие tombstone, замена последующим END. Возврат WAITING только после последнего байта ACK.
4. Stop до BEGIN, посередине BEGIN/DATA, до первого байта END, после первого и полного END,
   около RELEASE_ACK; обязательные прежние ответы сохранены, terminal один, sequence без gaps,
   после STOP_ACK данные старого поколения не выдаются.
5. Новый HELLO допередаёт начатый старый кадр и подавляет его callback относительно нового сеанса;
   незапущенные старые данные удаляются. Тот же nonce, включая recovery, не сбрасывает состояние.
6. Malformed/CRC/reserved/version/длина, направление до session guard, чужой nonce,
   replay/conflict/gaps/request order/unknown types, предельные счётчики, строгие Python-типы/часы,
   backpressure, сохранение непринятого суффикса и ограниченность retained memory.
7. Just-before/exact/after hold deadline, последний байт END, частичный RELEASE,
   Stop/RELEASE races и арифметика около uint64 max проверены **только в явно условной модели**.
8. Обязательная матрица, zero skips, optimized execution, before/after hashes и история evidence сохранены.
9. Независимое exact-version заключение — настоящий отчёт; общей приёмки/релиза он не выдаёт.

### Дополнительные независимые пробы критика

[Собственный код](evidence/device-fd1d/critic_probes.py) не импортирует авторские или conformance tests/reference
либо production codec. Управляющие кадры создаются и разбираются самостоятельно;
CRC массива дополнительно вычисляется побитно. Private counter injection применяется только
для недостижимых практически миллиардных границ; обычные сценарии используют публичный API.

- **4 699 разрезов**, то есть каждый байтовый префикс одного полного 4698-байтового вывода окна.
  В каждой точке поступают два Stop: начатый кадр заканчивается, terminal ровно один,
  оба STOP_ACK присутствуют, sequences непрерывны. До первого байта END получается ABORT,
  после него END; после первого STOP_ACK старых данных/terminal нет, dropped соответствует исходу.
- **919 разрезов** старого вывода окна при свежем HELLO: все внутренние позиции BEGIN,
  первого и последнего DATA, END/STATUS, дополнительные позиции остальных DATA.
  **399 разрезов** всех девяти проверенных типов управляющего вывода: HELLO_ACK/CAPS/CONFIG_ACK/
  ARM_ACK/STOP_ACK/STATUS/RELEASE_ACK/ABORT/ERROR. Старые completion callbacks не меняют новый сеанс.
- **80 окон** в RELEASE-loop: 20 для каждого сочетания rising/falling и порогов 1/4094.
  Независимо восстановлены точные коды и CRC; ACK проверен до последнего байта,
  повторные RELEASE не создают окна/повторный rearm.
- Все **256 типов** для current и foreign nonce, включая направление до session и неизвестные типы.
- **600 обязательных ответов** при детерминированных псевдослучайных input/read размерах;
  наблюдались 1282 случая backpressure, ни один ответ не потерян/дублирован.
  Сохранялись границы queue ≤8, current frame ≤544, RX ≤543, один прежний sample-buffer object.
- Предельный RX/request допускается единожды и распознаётся как точный повтор;
  следующий недопустимый ID требует свежего nonce, тот же HELLO recovery не отменяет.
- Tombstone предыдущего END не освобождает новый активный буфер; после следующего END старый RELEASE
  отклоняется, после ABORT остаётся допустимым без rearm остановленного режима.
- После прогрева и 5000 дополнительных GET_STATUS измеренная прибавка retained memory — **64 байта**.
  Это регрессионная проверка роста, не абсолютный бюджет Python/MCU или измерение latency.
- Отдельный PROVISIONAL случай: неверные API-вызовы на условной границе 5000 ms не меняют snapshot;
  последующий корректный tick выполняет описанное условное истечение.

Это параметризованные циклы внутри 11 unittest, а не тысячи формально отдельных тестов.
Первый успешный набор из девяти проб также сохранён; затем условный случай выделен отдельно
и покрытие управляющих кадров расширено. Неуспешных личных прогонов не было.
История прежнего статического замечания по late RELEASE сохранена в исходном `diagnoses.md`:
наличия несохранённого failing run старой реализации не выдумываем.

## Проверенные свойства кода

`write()` сначала проверяет тип, размер и время; до каждого RX-байта резервирует три места ответов.
Входной суффикс остаётся у caller. `_window_descriptor()` формирует DATA лениво, не собирает
закодированное окно в очередь. Samples buffer единственный, фиксированный, без истории окон.

Первый положительный `read` фиксирует sequence; END фиксируется при первом байте.
Stop отменяет продолжение, но сохраняет текущий frame и обязательные ответы.
Барьер заканчивается ровно последним байтом STOP_ACK, даже если STATUS ещё ожидает передачи.
Epoch проверяется перед callback; новый HELLO/reset не допускает старых мутаций.
RELEASE проверяет принадлежность удерживаемого буфера текущим generation/window, а не только
совпадение сохранённого tombstone. Документированная прежняя проблема этим закрыта.

Возможности согласованы: capability_bits=9, mode_bits=2, source_bits=1, edge_bits=3,
pre_count=1, pre0/1/2=0. Auto/Single/external/pretrigger не обещаны и отвергаются.
Номинальные 50 kS/s выводятся из делителей; мгновенный trigger и детерминированные rail-коды
не выдаются за измеренную частоту, аналоговый threshold detector или перегрузку тракта.
Immutable provenance явно сообщает simulator/draft/nominal/synthetic и условный timeout;
лишнего wire-поля не вводится.

## Спорный timeout и незакрытые уровни

**PROVISIONAL остаётся PROVISIONAL.** Условная модель считает 5000 ms от последнего принятого
байта END, при elapsed ≥5000 выдаёт ERROR / STATUS.reason=TRANSFER_TIMEOUT (3), отменяет
продолжение, сохраняет END/tombstone без второго terminal. RELEASE после срока освобождает
буфер без rearm; Stop может завершить остановку. Это проверенное поведение кандидата,
**не одобренное нормативное толкование** общего wire draft.

На личном read-only просмотре PR14 около 14:45 UTC ответ владельца A на
[уточнение #6097915092](https://github.com/font-weight/stm32_motortester/pull/14#issuecomment-6097915092)
по-прежнему отсутствовал. До ответа/нового exact source и требуемых совместных ревью
нельзя использовать данный PASS как основание принятия точки отсчёта/причины timeout.
Приёмка общего контракта этим отчётом не производится; его неизвестные обязательные свидетельства
нельзя заменить компонентной оценкой. #42 заранее разрешает такую ограниченную программную проверку.

Не проверены и не принимаются: physical USB/serial, Windows 10 и установщик,
АЦП/DMA/память STM32, реальные частоты/пороги, GUI-привязка этого peer,
интеграция WindowReceiver/записи/файлов, Auto/Single/external/pretrigger,
LV-001, зажигание, автомобиль, software-ready или release-ready MVP.
`trigger()` является явным синтетическим событием. Disconnect/reset здесь только модель API.

Исторические ограничения старой базы не отменяются 291 успешным тестом.
После переноса в интеграционную ветку необходимо проверить итоговую композицию и точный SHA;
эта оценка автоматически не переносится на другой commit, merge tree или новый общий source.
В частности, более строгие миллиардные config/window пределы HOST-006 остаются отдельно
документированным ограничением совместимости, а не молчаливым repin или заявлением полного firmware parity.
