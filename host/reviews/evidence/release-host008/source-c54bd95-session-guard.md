# A-004: проверка сеанса и повторов

Черновой модуль `firmware/protocol/mt_session.h/c` выполняет только
проверку входящей последовательности команд. Он не управляет таймером,
АЦП, DMA или USB и не заменяет автомат захвата.

## Состояние и действия

Хранится текущий nonce, следующий sequence, последний request_id и
последнее принятое сообщение. Память ограничена одним сообщением:
на проверенном x86-64 ABI sizeof(mt_session)=568 байт. Это не измерение ARM.

После корректного нового HELLO возвращается NEW_HELLO. Диспетчер обязан
остановить старый захват, сбросить конфигурацию/счётчики и согласованно
очистить/допередать TX, затем поставить HELLO_ACK. Само принятие нового nonce
не выполняет эти действия.

Для обычного сообщения:
1. Неверное направление требует восстановления.
2. Без согласованного сеанса возвращается NEED_HELLO.
3. Чужой nonce отбрасывается без изменения текущего сеанса.
4. Точный повтор непосредственно предыдущего сообщения игнорируется.
5. Конфликт такого повтора или пропуск sequence выключает приём до HELLO.
6. Правильный заголовок потребляет sequence/request даже при неверном
   обычном payload: диспетчер затем отправит соответствующий ERROR.

Сравниваются смысловые поля заголовка, длина и использованные байты payload.
Padding структуры и неиспользованный остаток массива не являются данными wire.

## Неоднозначности, уточнённые в этом draft

Sequence идёт непрерывно с 2. Request_id строго возрастает и не меньше 2;
пропуски request_id разрешены. Значение UINT32_MAX не используется для
sequence/request; требуется новый handshake до этой границы. Эти уточнения
общего контракта требуют ревью обеих сторон, не объявлены принятыми.

После восстановления сохраняется прежний nonce. Повтор того же HELLO
игнорируется даже в неактивном состоянии: ПК должен выбрать новый nonce.
Инициализация после настоящего сброса транспорта забывает nonce; это не
доказательство отсутствия его прежнего использования.

## Что подключить дальше

На ACCEPT сначала разобрать payload, затем проверить допустимость действия
в текущем состоянии и только потом исполнять. На RECOVERY/EXHAUSTED немедленно
выполнить безопасное прекращение захвата через будущий диспетчер.
На DUPLICATE не исполнять команду и не создавать повторный ACK.
INVALID_HELLO не меняет рабочий сеанс.

Обычная CONFIG с неверной длиной может дать ACCEPT у RX guard, но LENGTH
у parser: это намеренное разделение заголовка и содержания. ACCEPT здесь
не означает успешную настройку устройства.

## Проверки автора

В native Dot-среде GCC 14.2.0 выполнены строгая C11-сборка и авторские
тесты HELLO, nonce/recovery, sequence/replay, request gaps, неверного сеанса,
ошибочного payload, пределов идентификаторов и аргументов.
ASan+UBSan прошли с ASAN_OPTIONS=detect_leaks=0; проверка утечек не заявляется.
Точные команды и хеши — [a004-native.txt](evidence/a004-native.txt).

```sh
cc -std=c11 -O2 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Werror \
  firmware/protocol/mt_command.c firmware/protocol/mt_session.c \
  tests/protocol/test_mt_session.c -o /tmp/test_mt_session
/tmp/test_mt_session
```

Независимый критик дополнительно проверяет неизменный опубликованный SHA.
Авторские тесты и этот текст сами по себе не дают PASS.
ARM, полный диспетчер, native USB и физические измерения остаются открытыми.

## Исправление правил Stop в общем контракте

В этом же draft уточняется: номер TX предварителен до первого положительного
принятия байтов транспортом; отмена неподанного кадра не расходует номер.
ABORT создаётся только для реально выделенного нетерминального окна.
Stop без такого окна и повторный Stop не создают фантомный или второй ABORT.
Для отмены захвата до BEGIN допускается ранний ABORT как событие без массива.

Это правила будущего TX/диспетчера, не функции mt_session. Их отдельные
исполняемые сценарии и совместное ревью обязательны.
