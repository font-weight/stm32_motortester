## Результат

В публичном API текущего HOST-006 новый обычный запрос во время ожидания STOP_ACK
не может появиться. Это совместимо с предложенным запретом, но **не является
реализацией или испытанием ещё отсутствующих GET_STATUS/RELEASE API**.

- `session.py:283–286, 316–327`: configure/arm вызывают `_available`, который
  отклоняет вызов при pending Stop независимо от наличия обычного запроса.
- `329–335`: второй Stop также отвергается до ответа.
- `459–471`: единственное автоматическое создание GET_CAPS находится внутри
  принятого HELLO_ACK; оно выполняется до возврата из receive. Stop в HELLO
  недоступен, а после перехода в CAPS GET_CAPS уже является более ранним запросом.
- GET_STATUS (type6), RELEASE_WINDOW (type7), повторный явный GET_CAPS и общий
  публичный `send/queue` в классе отсутствуют. Поддерживаемые публичные источники
  обычных команд: configure, arm и автоматический GET_CAPS.
- `337–349`: уже поставленный GET_CAPS/CONFIG/ARM завершается перед Stop;
  `432–438`: прежний ответ разбирается, STOP_ACK до него не допускается.
- `472–495`: прежний CAPS/CONFIG/ARM ответ закрывает обычный запрос, сохраняя Stop;
  ARM_ACK при этом не выдаёт событие ARMED. Барьер снимается валидным STOP_ACK
  (`496–507`) либо переходом в RECOVERY, где дальнейшие обычные команды запрещены.

**HELLO recovery не означает свободный start во время drain.** `start` (`272–281`)
разрешён только в IDLE/RECOVERY и с новым nonce. Прямой start при pending Stop
возвращает STATE без изменения снимка/билета. После настоящего timeout,
transport-lost, unknown-write или protocol/downstream fault контроллер выдаёт
reset_transport/preserve_fragments; внешний владелец завершает восстановление
транспорта и только затем вызывает start. Нельзя обозначать нормальную работу
транспорта выдуманным fault ради перезапуска. Отдельного API произвольного
принудительного re-handshake текущая задача не обещает.

## Узкое предложение владельцу host

Production-исправление текущего публичного API для соблюдения предложенного запрета
не установлено. Достаточен документальный/регрессионный delta после согласования политики:

1. Явно написать в session-controller.md: «Пока Stop ожидает ответа, новые обычные
   запросы не планируются. Уже поставленный запрос и его ответ завершаются по порядку.
   GET_CAPS сейчас только автоматический этап handshake; GET_STATUS и RELEASE не
   реализованы. При их добавлении они также обязаны соблюдать общий Stop barrier».
2. Добавить адресный product regression: pending Stop без обычного запроса и после
   потребления прежнего CAPS/CONFIG/ARM ответа по-прежнему отвергает configure/arm;
   STOP_ACK разрешает дальнейший допустимый запрос; fault → reset → свежий HELLO
   не повторяет старые байты. Большая часть поведения уже покрыта существующими
   тестами; здесь полезна явная привязка к CA-CTRL-4.
3. При будущем добавлении API type2/6/7 обеспечить общий admission guard до `_queue`:
   приватный `_queue` сам по себе проверяет время/ёмкость, а не публичный Stop barrier.
   Нельзя объявлять отсутствие этих API положительным тестом их запрета или тестировать
   приватный обход как поддерживаемый пользовательский способ отправки.

Это рекомендация, не изменение shared spec и не согласование политики от имени B.
CA-CTRL-4 требует явно опубликованного решения A/B и exact-SHA проверки обеих сторон.
Исходный HOST-006 PASS остаётся ограниченным прежним scope; новых оценок всему
wire/CTRL/USB/Windows/прибору здесь нет. Production, product tests и shared документы не менялись.
