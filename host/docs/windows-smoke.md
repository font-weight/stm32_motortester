## Что исправляется и что ещё неизвестно

В запуске `38208738974` для исходников
`b8966df26bd49c53fdc089eae622f69f18f40253` прошли 290 Windows source-тестов,
20 синтетических окон и PyInstaller EXE/COLLECT. Задание отменено через
30 минут; cleanup завершил оставшийся процесс Motortester. Успешный frozen
screenshot, готовый ZIP и его контрольные суммы не подтверждены.

Прежний рецепт писал команду только после завершения дочернего процесса
и не ограничивал время frozen smoke. Поэтому журнал не показывал момент

недостаточно, чтобы выбрать между запуском bootloader, импортом GUI,
Windows/Qt platform, исключением с диалогом или этапом screenshot/выхода.
Различие между offscreen source-тестами и native frozen-окном само по себе
не доказывает причину.

Эта правка добавляет ограничение ожидания, наблюдаемость и отказ без
интерактивного Python traceback-диалога внутри служебного launcher-сценария.
Она не означает успешного повторного запуска на Windows. Реальный повтор
и независимое ревью точной версии обязательны отдельно.

## Поведение сборки

Обычная команда сборки из `host/`, на Windows x64 с обычным CPython 3.13.16
и чистым проверенным checkout:

```powershell
py -3.13 packaging\build_windows.py --output C:\motortester-build\smoke-check-1
```

Выходная папка должна быть новой. До каждого дочернего процесса в `build.log`
записываются и сбрасываются START, UTC, точная командная строка, ограничение
времени и запрошенная Qt platform. stdout/stderr ребёнка пишутся прямо в
журнал. END содержит код завершения и длительность. Ошибка запуска, timeout
и недостоверный screenshot оставляют явную запись об отказе.

На `Motortester.exe --screenshot ...` отведено **60 секунд**, затем до
**5 секунд** на завершение и ожидание прямого дочернего процесса. Это политика
проверки сборки, не timeout USB, wire-протокола или захвата сигнала. При
неподтверждённом cleanup сборка также завершается ошибкой; успешное завершение
процесса не выдумывается. Механизм не обещает завершить произвольные процессы-
потомки, если приложение начнёт их создавать: это надо проверять на реальной
Windows-сборке. Обычная программа сейчас запускается как onedir.

Рецепт сохраняет native Windows Qt platform: `QT_QPA_PLATFORM` удаляется из
унаследованной среды и не заменяется на offscreen для frozen smoke. Для
source-тестов offscreen остаётся отдельным параметром, как и раньше.

## Служебный launcher и свидетельство

Команда `Motortester.exe --screenshot OUTPUT.png` до GUI import создаёт
UTF-8 JSON-файл `OUTPUT.png.smoke.json`. Обычный интерактивный запуск делегируется
GUI без изменения аргументов. GUI/screenshot-функция приложения не изменена.

Проверяются новые имена PNG и receipt. Оба файла резервируются исключительно;
существующий файл, старое успешное свидетельство или конкурентное создание
не перезаписываются. При ошибке частичный PNG/receipt сохраняются. Повторять
следует с новым именем, а не удалять предыдущие доказательства автоматически.
Родительская папка должна уже существовать. Это сценарий в собственной папке
сборки, не защита от злонамеренной подмены каталогов другим процессом.

В receipt записываются UTC-фазы:

1. entry, до GUI import
2. gui-import
3. gui-imported
4. screenshot, перед существующим файловым round-trip/окном
5. png-validation
6. complete

Импорт или выполнение с ошибкой завершаются ненулевым кодом и статусом failed,
с ограниченным traceback. Для ошибок Qt callbacks используется локальный
smoke-only excepthook; ошибка не превращается в PASS. Наличие консоли не
требуется. Если сам receipt записать невозможно, возвращается ошибка;
программа не утверждает, что диагностический файл создан. Ошибка bootloader
до входа в launcher или зависание нативного кода по-прежнему могут не дать
Python-диагностику; внешний deadline ограничивает ожидание такого ребёнка.

Успех требует одновременно:

- Нулевой код завершения процесса
- Валидный JSON схемы 1, не более 64 KiB, со всеми терминальными фазами
- Actual Windows `sys.platform=win32`, `sys.frozen=True`, Qt platform `windows`
- Реальный PNG, декодированный Qt без ошибки, с ненулевыми размерами
- Не более 32 MiB PNG, 8192 пикселей по каждой стороне и 16 миллионов пикселей
- Совпадение размера и SHA-256 PNG с декодированным результатом в receipt

Build-side проверка JSON/хеша не импортирует Qt в исходный bootstrap Python:
декодирование делает сам frozen-ребёнок, а родитель связывает receipt с теми
же байтами. Один старый PNG или один статус passed недостаточен. Source/
offscreen receipt не может удовлетворить обязательную frozen Windows проверку.

При ненулевом exit, timeout, отсутствующем/повреждённом PNG/receipt сборка
останавливается до записи успешного build-manifest и ZIP. Уже полученные
wheelhouse, EXE, журнал и частичные файлы остаются для диагностики. Успешный
receipt включается в build-manifest, его файл входит в SHA256SUMS вместе с PNG.
Это всё ещё кандидат, не принятый Windows-релиз и не проверка USB.

Из `host/` с реальными GUI-зависимостями:

```sh

QT_QPA_PLATFORM=offscreen python -O -m unittest discover -s tests -p test_windows_smoke.py -v

python -O -m unittest discover -s tests -p test_windows_archive.py -v
QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -v
QT_QPA_PLATFORM=offscreen python -O -m unittest discover -s tests -v
```

Проверяются нормальный путь, импорт/исключение/Qt callback, отсутствие консоли,
Unicode/пробелы в путях, старые и конкурирующие выходы, невалидный PNG/JSON,
изменённый хеш, ненулевой exit, настоящий зависший контролируемый ребёнок,
его завершение/ожидание и запрет создания успешного manifest/ZIP при отказе.
Это source/fake-backed проверки: они не доказывают поведение Windows bootloader.

## Передача команде A/root

До запуска сохранить exact source SHA и workflow SHA раздельно; использовать
новую выходную папку. Сохранить build.log, PNG и `.smoke.json` даже при отказе.
Успешный повтор должен подтвердить реальный native Qt platform, все фазы,
нулевой exit, отсутствие оставшегося прямого ребёнка, PNG/receipt, manifest,
архивы и их SHA-256. Первая ограниченная ошибка с понятной фазой полезна для
диагностики, но не является PASS. Чистая Windows 10 и физический USB остаются
отдельными незакрытыми испытаниями.

Исходный компонент PR116 был основан на b8966df без нового pyserial-рецепта.
Текущая композиция уже сохраняет serial-проверку и зависимости PR108 вместе
с GUI smoke, как описано выше. При следующих переносах обе проверки должны
сохраняться; старый компонентный рецепт нельзя накладывать целиком поверх этой
композиции.

## 17.10.2026: ограниченный состав runtime для Windows 10 1809+ x64

Новый кандидат продолжает приложение `244b0786a18fed19a9e708bb815150475ddd193f`
(tree `0c0e61fb8aadd4a4380e2d7e0b8818e4c9da0d5e`) только изменением упаковки.
Целевой минимум — **Windows 10 версии 1809+ x64**, также требуется отдельная
проверка фактической целевой ОС. Windows 7/8 и произвольные урезанные редакции
не поддерживаются этим решением. Это не результат новой Windows-сборки:
предыдущие журналы и run18 остаются историческими и не меняются.

После `Analysis`, до `PYZ`/`EXE`/`COLLECT`, spec вызывает чистую функцию
`packaging/select_windows_runtime.py`. Она исключает только 47 явно
перечисленных полных относительных TOC destinations: 29 `api-ms-win-core-`
и 14 `api-ms-win-crt-` DLL, `ucrtbase.dll`, `libcrypto-3-x64.dll`,
`libssl-3-x64.dll` и `PySide6/plugins/tls/qopensslbackend.dll`.
Список относится к содержимому `_internal`; этого префикса в TOC нет.
Проверка не удаляет файлы из исходных зависимостей, готовой папки или ZIP.

Основания выбора:

- [Microsoft: развёртывание UCRT](https://learn.microsoft.com/en-us/cpp/windows/universal-crt-deployment?view=msvc-170):
  Windows 10+ предоставляет системный UCRT; системный вариант имеет приоритет
  перед локальной копией. [Разрешение API-set](https://learn.microsoft.com/en-us/windows/win32/apiindex/api-set-loader-operation)
  выполняется ОС. Нужные API продолжают использоваться; отсутствие прямого
  импортёра не доказывает, что API или UCRT не нужны.
- [PyInstaller 6.22.3: TOC](https://pyinstaller.org/en/v6.22.3/advanced-topics.html#the-table-of-contents-toc-lists-and-the-tree-class)
  допускает редактирование списков `Analysis` перед целями сборки.
  В сохранённом официальном wheel 6.22.3 (`SHA-256`
  `500bd58c7bf7e584a8435adccbd763a0b918d5c12b08d74ff50fd79b2915458b`)
  `PyInstaller/depend/dylib.py:139–148` прямо рассматривает отсутствие
  необходимости включать эти системные компоненты для Windows 10+.
- [Qt: состав SSL-пакета](https://doc.qt.io/qt-6/ssl.html#considerations-while-packaging-your-application)
  разрешает не поставлять OpenSSL вместе с `qopensslbackend`, если нужны
  возможности Schannel. Тот же текст есть в сохранённом Qt 6.12.0,
  `src/network/doc/src/ssl.qdoc:77–86`.
  [QSslSocket::activeBackend](https://doc.qt.io/qt-6.12/qsslsocket.html#activeBackend)
  описывает выбор Schannel на Windows при отсутствии OpenSSL backend.
  Это основание структурного выбора, не свидетельство выполненного TLS.

Обязательно сохраняются `PySide6/Qt6Network.dll`, `PySide6/QtNetwork.pyd`,
`PySide6/plugins/tls/qschannelbackend.dll`, `_ssl.pyd`, `_hashlib.pyd`,
`libcrypto-3.dll`, `libssl-3.dll`. Последняя пара принадлежит отдельной
зависимости CPython, без суффикса `-x64`; она не заменяется и не удаляется.
Отсутствие любого из семи путей прерывает сборку. Четыре DLL должны иметь
TOC type `BINARY`; три `.pyd` допускают `EXTENSION` или `BINARY`.
`qcertonlybackend`, VC runtimes и все остальные строки сохраняются без
изменения полей и порядка. Это не проверка происхождения их байтов или прав.

Регистр и разделители Windows учитываются при сравнении полного destination.
Некорректные строки/типы, абсолютные и обходные пути, ADS, имена устройств,
Win32-псевдонимы и совпадающие нормализованные пути вызывают отказ.
Выбранный basename в другом каталоге также требует отдельного ревью.
Неизвестные имена семейств `api-ms-win-core-`/`api-ms-win-crt-`,
`ucrtbase*.dll`, `qopensslbackend*.dll` и `libcrypto-`/`libssl-` DLL с `-x64`
вызывают отказ; это **не** маска для удаления. Другие семейства API-set
остаются как есть, поэтому исключение любых возможных системных DLL
не заявляется. Одинаковые VC-runtime basenames в разных каталогах допустимы.

Все 47 исключений могут уже отсутствовать в чистом `Analysis`. Это не ошибка,
если обязательные компоненты есть. Функция возвращает фактически исключённое
подмножество; spec записывает его имена и число из 47 в `build.log`.
Пути источников остаются входными данными: функция не открывает и не хеширует
нативные файлы и не требует старых байтов при пересборке модифицированной
зависимости. Обновление списка или иной состав зависимостей требует ревью.

Штатный PyInstaller Qt-hook **может проверять ambient OpenSSL во время
Analysis до фильтра**. Это изменение не запрещает такой build-time probe.
Отсутствие возможных динамических загрузок, взаимозаменяемость TLS backend
во всех функциях и успешность Schannel/TLS не заявляются. У приложения нет
заявленной TLS-функции. Только для положительного утверждения о Schannel
нужна отдельная frozen QtNetwork/`QSslSocket` capability-проверка; новый
launcher mode или TLS handshake здесь не добавлены.

### Проверки и последующая передача

Чистые tests `test_windows_runtime_selection.py` выполняются обычным Python
и с `-O`. Они проверяют все 47 имён, частичное/нулевое наличие исключений,
каждый обязательный компонент, отрицательные пути/типы/коллизии/новые имена,
сохранение CPython/VC runtime и неизменность входа. Настоящий spec выполняется
с инертными целями PyInstaller из посторонней рабочей папки: отфильтрованный
TOC должен попасть в `COLLECT`, а отказ должен предшествовать всем целям.
Это source-проверки, а не исполнение Windows EXE.

Новая версия требует отдельного application commit/tree, исходного ZIP,
идентичностей spec/helper и актуального независимого ревью. Совпадение
прежних 23 runtime-исходников не переносит старую оценку или Windows-результат.
Команда A/root должна явно согласовать новые source/recombination pins и
consumer/workflow. Старый observer, ожидающий фиксированные 46 DLL, нельзя
применять без изменения семантики: отсутствие файла не подтверждает его
происхождение. Прежние counts и отчёты не переписываются.

Штатный рецепт остаётся обязательным: полные source-тесты, frozen serial,
native-QPA GUI и recording smokes проверяют уже уменьшенный состав.
В фактической onedir-папке и конечном ZIP отдельно проверить отсутствие
всех 47 destinations и наличие семи обязательных, сохранить новые байты,
хеши и receipts. После успешных smoke-тестов ничего не удалять из пакета.
Нужен новый Windows-прогон; Linux/offscreen и run18 его не заменяют.

На чистой Windows 10 x64 без Python/Qt/Temurin/MySQL/OpenSSL в окружении
проверить запуск/закрытие, NumPy/отображение и record/open/save, доступность
API-set/private CRT и остальные ранее объявленные сценарии. Если передача
пользователю предшествует этому опыту, результат Server 2022 можно назвать
только проверенным там кандидатом для первого Windows 10 испытания.
Ни Windows 10 acceptance, ни физический USB/плата/Stop, ни полнота исходников,
лицензий и прав распространения этим фильтром не подтверждаются.
