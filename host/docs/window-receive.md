# HOST-004: ограниченная экспериментальная приёмка окна

Статус: **DRAFT, общий wire-контракт не принят**. Задача
[HOST-004 #17](https://github.com/font-weight/stm32_motortester/issues/17).
База HOST-002: `c89c12df984390b34785eba81665abd6418658e2`.
Единственный источник wire-полей —
[draft A, SHA 124b3f32e1e7f7282bce283baa4c9406d4d72950](https://github.com/font-weight/stm32_motortester/blob/124b3f32e1e7f7282bce283baa4c9406d4d72950/protocol/wire-v0.1.md).
Этот модуль не создаёт новый вариант общего протокола.

## Граница и предпосылки

`motortester/window.py` принимает один уже допущенный внешним диспетчером
`Frame` из [HOST-002](wire-adapter.md) и собирает одно окно. Диспетчер обязан
сначала проверить diagnostics потокового decoder, направление, handshake,
сеанс, sequence и ответы на команды. Успех byte codec сам по себе этого не
доказывает. Конструктор получает принятые снаружи CONFIG и контекст ARM;
согласование CAPS/CONFIG, переоткрытие транспорта и восстановление здесь
отсутствуют. Session дополнительно сравнивается с ожидаемым, а request_id
события должен быть нулём.

Модуль не открывает USB/COM, не передаёт ACK/RELEASE/STOP, не назначает TX
sequence, не реализует Auto/Normal/Single как состояния прибора и не меняет
модель записи, `.mtcap`, GUI, прошивку или общие документы. Повторный запуск
сборщика требует явного `reset()`; это не команда вооружения устройства.

Все приведённые проверки выполнены или предназначены для **синтетических
данных**. Наличие полного результата не доказывает происхождение из прибора,
аппаратную целостность, точность времени, Windows 10, физический USB или
готовность MVP. `protocol_source_sha` и `validation_scope="draft_window_receive"`
есть в каждом результате. Статус общего контракта остаётся DRAFT даже при
`semantic_checks_complete=True`.

## API и неизменяемые результаты

Только стандартная библиотека Python; объекты `ExpectedContext`,
`BeginMetadata`, `SampleBlock` и возвращаемый `WindowResult` — frozen dataclass.
Их вложенные коллекции на выходе — только tuple. Один владелец сборщика,
без конкурентных вызовов и внутренних очередей результатов.

- `ExpectedContext(session, generation, config_id, acquisition_mode, source,
  edge, level_code, pretrigger_samples, profile=1)`: точные `int`, без bool,
  float или подклассов. Session — uint64 ненулевой; generation — uint32 от 2
  (request_id успешного ARM); config_id — uint32 от 1. Режим 0/1/2, source 0/1,
  edge 0/1, level 1…4094, pretrigger 0/512/1024, profile только 1. Предполагается,
  что конкретная комбинация уже согласована снаружи.
- `WindowReceiver(context).feed(frame, now_ms) -> WindowResult | None` принимает
  именно HOST-002 `Frame`, повторно проверяя типы и пределы его полей. Payload
  — именно bytes до 512 байт. Числовой диапазон sequence проверяется, его порядок
  остаётся обязанностью диспетчера.
- `tick(now_ms)` проверяет отсутствие прогресса; вызывается регулярно и при
  отсутствии новых кадров. `disconnect(now_ms)` завершает активное окно с
  DISCONNECT, если прежде не истёк срок.
- `reset()` выдаёт RESET с неполными фрагментами, только если окно активно;
  затем очищает временную базу и разрешает новый BEGIN. Повторный reset без
  активного окна ничего не выдаёт. Для другого контекста создать новый сборщик.
- `BeginMetadata` содержит все исходные поля BEGIN, включая raw
  external_edge_id, quality_flags и номинальные параметры таймера.
- `SampleBlock(offset, samples)` хранит принятый исходный блок: смещение в
  отсчётах и tuple кодов. Границы исходных блоков сохраняются.

`WindowResult.complete` означает только: приняты 2048 отсчётов, END имеет
согласованные идентификаторы/длину/count/reserved, а CRC совпадает. Только тогда
`samples` содержит полный tuple и `samples_crc32` — CRC исходных 4096 байт.
При неполноте оба поля равны None, даже если все 2048 отсчётов уже получены,
но END не пришёл или CRC не совпала. `reason` — локальный `WindowCode`,
`abort_reason` содержит wire-reason только для принятого WINDOW_ABORT.

`fragments` содержит проверенные блоки и при успехе, и при неполноте.
`missing_ranges` — tuple полуоткрытых диапазонов `[начало, конец)` в отсчётах;
при последовательной передаче это отсутствующий суффикс или пустой tuple.
Пустой список пропусков **не означает успех**: при ошибке END/CRC возможны все
отсчёты без подтверждённого полного окна. Нули не подставляются, фрагменты не
перезаписываются, преобразование неполного результата в `.mtcap` отсутствует.

`rail_observed` вычисляется по принятым фрагментам: найден 0 либо 4095.
Для неполного окна False не исключает rail в отсутствующем суффиксе.
После полного END проверяется соответствие raw bit 1 этому наблюдению.
Несоответствие отражается в `metadata_issues=("RAIL_FLAG_MISMATCH",)`;
исходные коды и флаг сохраняются. Это локальная проверка согласованности уже
определённого bit 1, не новая неопределённость общего контракта. Полнота массива
при этом остаётся True, семантическая проверка — False. Крайний код сам по себе
не доказывает аналоговую перегрузку или отсутствие искры.

`deferred_checks` содержит только фактически отложенные проверки общего draft.
`semantic_checks_complete = complete and not deferred_checks and not metadata_issues`.
Это свойство ограничено перечисленными локальными проверками; оно не является
разрешением на передачу RELEASE, подтверждением сеанса или приёмкой прибора.

## Что проверяется

Все поля little-endian. Точные длины: BEGIN 40, DATA 12+2N при N=1…250,
END 16, ABORT 12. В BEGIN проверяются ожидаемые session/generation/config/profile,
непустой window_id, channel 0, sample_count 2048, принятые source/edge/level/pre,
профильные номинальные timer_clock_hz 72000000, timer_psc 71, timer_arr 19.
Такое совпадение не является измерением частоты. Типы запуска 0/1/2,
source/edge 0/1, mask quality_flags 0x7 и bit0, соответствующий auto_timeout,
проверяются. Bit2 сохраняется без выдуманного условия «тогда и только тогда»
для внешнего запуска; аппаратная неопределённость внешней привязки остаётся.

Для реального запуска trigger_index=pretrigger_samples; analog требует source 0
и external_edge_id 0. External требует source 1; в Normal/Single его ID ненулевой.
Auto_timeout разрешён только при acquisition_mode 0, index 0xffff и external ID 0.
Условия Auto с реальным внешним событием рассматриваются отдельно ниже.

DATA принимает только коды 0…4095 и допустимые offset/count до выделения массива
кодов. Принятые блоки идут последовательно. Разрешён точный повтор **любого**
ранее принятого исходного блока с теми же offset/count/кодами и текущими ID;
порядок sequence уже должен быть проверен снаружи. Дубль не копится повторно,
не меняет CRC и не продлевает срок. Совпадающий по значениям подотрезок или
объединение блоков не становится точным дублем. Пропуск, конфликт/перекрытие,
изменённые ID дают неполноту с прежними фрагментами; новый блок не принимается.

END требует 2048 принятых отсчётов и count 2048; CRC-32/ISO-HDLC вычисляется
по исходным4096 little-endian байтам кодов в порядке offset. Reserved END/ABORT
должны быть 0. ABORT reason разрешён 1…6 и сохраняется в отдельном поле.

Неправильный тип сообщения либо некорректный payload, доставленный этому узлу,
завершает активное окно как неполное. Без активного окна неверный BEGIN или
DATA/END/ABORT даёт один результат с begin=None, пустыми фрагментами и
missing_ranges=((0,2048),); после этого требуется reset. При уже выданном
терминальном результате последующие корректные по API события игнорируются.
Валидация типов, размеров и времени действует даже после завершения.

## Совместимость с более новым непринятым draft

В [PR14, SHA 1ed8f3f45ec56f0c9d4cc1bebcede4240b357348, строка135](https://github.com/font-weight/stm32_motortester/blob/1ed8f3f45ec56f0c9d4cc1bebcede4240b357348/protocol/wire-v0.1.md#L135)
явно допускается WINDOW_ABORT выделенного окна до BEGIN. HOST-004 остаётся
закреплён на `124b3f32`; новый draft не подменяет источник этой итерации.
Будущий внешний диспетчер сеанса должен проверить и устранить дубли такого
раннего ABORT по session/generation/window_id, затем сохранить отдельное
событие отмены без BEGIN и без принятых отсчётов. Его не следует подавать как
обычное событие активного окна этому сборщику. Локальный ORDER при idle —
защита границы этого API, **не утверждение о недопустимости раннего ABORT в
общем wire**. Фиктивный BEGIN или нулевой массив не создаются. Полная адаптация
раннего ABORT требует отдельной итерации с явным обновлением source pin.
Новые TX/request/ACK-правила также остаются за границей этого узла.

## Время и порядок отказа: локальный API

Сам срок 3000 ms задан в
[строке125 закреплённого draft](https://github.com/font-weight/stm32_motortester/blob/124b3f32e1e7f7282bce283baa4c9406d4d72950/protocol/wire-v0.1.md#L125):
при отсутствии прогресса передачи ПК прерывает окно. Ожидание запуска
Normal/Single само по себе не является таким timeout.

Для этого Python API явно выбраны следующие детали границы. `now_ms` — точный
int в 0…2**64−1, монотонный без rollover. Одинаковые метки допустимы; годятся
`time.monotonic_ns() // 1_000_000`, календарные часы не годятся.

1. Сначала проверяются тип/размер/диапазоны всех входных аргументов и откат
   времени. Ошибка WindowError не меняет никаких полей сборщика, не истекает
   окно и не продвигает временную базу, даже при переданном now_ms за сроком.
2. Корректный вызов обновляет базу проверки монотонности. До обработки текущего
   события проверяется `now_ms - last_progress_ms >= 3000`. При равенстве
   выдаётся TIMEOUT; поздний DATA/END/ABORT, даже семантически неправильный,
   уже не обрабатывается. Disconnect также сначала проверяет этот срок.
3. Прогрессом являются только первый принятый BEGIN и новые принятые отсчёты.
   Дубли, ticks и пустое ожидание прогресс не обновляют. До BEGIN срока нет.
4. Каждый кандидат выдаёт не более одного результата. Истёкший/закрытый
   сборщик не запускается автоматически. Reset намеренно не имеет аргумента
   времени: активное окно получает RESET, временная база очищается.

Это описанные host-local правила границы, а не дополнительный wire-контракт.
Срок приёма целого окна отличается от межбайтового и полного срока кадра в
HOST-002. Физические задержки USB этими тестами не измеряются.

## Диагностика и границы ресурсов

Ошибки вызова `WindowError(ValueError)` имеют фиксированный русский текст без
копирования входных данных и `.code`: ARGUMENT, RANGE, PAYLOAD_SIZE,
CLOCK_ROLLBACK. Ошибки корректно типизированного протокола возвращаются в
`WindowResult`, а не теряют принятые фрагменты через исключение.

Локальные reason: COMPLETE; TYPE/REQUEST/SESSION; CONTEXT/IDENTITY;
LENGTH/ENUM/RESERVED/BOUNDS/ADC; ORDER/OVERLAP; COUNT/CRC/QUALITY;
ABORT/TIMEOUT/DISCONNECT/RESET. CONTEXT означает несогласованные принятые
настройки или метаданные запуска; IDENTITY — generation/window; BOUNDS —
неверный диапазон поля; COUNT — число отсчётов BEGIN/END; QUALITY —
несогласованность bit0 и trigger_kind. Имена не являются wire enum.

Пределы проверяются до копирования payload/распаковки кодов. На входе не более
512 байт, в блоке не более 250 кодов; суммарно не более 2048 кодов и 2048 границ
блоков (худший случай — блоки по одному отсчёту). Дубли и повторные ошибки
не создают историю. CRC обновляется по каждому новому блоку. При полном
результате создаётся tuple 2048 ссылок на коды; фрагменты остаются исходными.
После результата сборщик освобождает свои ссылки на них. Python-объекты имеют
накладные расходы: это границы размера данных, не обещание расхода 4096 байт
RAM приложением или измерение пропускной способности.

## Неустранённые неоднозначности общего draft

[Строка141](https://github.com/font-weight/stm32_motortester/blob/124b3f32e1e7f7282bce283baa4c9406d4d72950/protocol/wire-v0.1.md#L141)
говорит о ненулевом счётчике внешнего события и одновременно об ID 0 для Auto.
Для acquisition_mode=Auto и trigger_kind=external модуль сохраняет любое raw
external_edge_id и всегда добавляет `deferred_checks=("AUTO_EXTERNAL_EDGE_ID",)`.
Даже правдоподобный ненулевой ID не делает semantic_checks_complete=True.
Полный массив/CRC может быть доступен как draft-свидетельство, но семантика
этого сочетания не объявляется принятой. Уточнение принадлежит владельцу A.

Момент назначения TX sequence при сериализации
[строка68](https://github.com/font-weight/stm32_motortester/blob/124b3f32e1e7f7282bce283baa4c9406d4d72950/protocol/wire-v0.1.md#L68)
и точка необратимости END по первому байту USB TX FIFO
[строка131](https://github.com/font-weight/stm32_motortester/blob/124b3f32e1e7f7282bce283baa4c9406d4d72950/protocol/wire-v0.1.md#L131)
здесь не разрешаются: приёмник не назначает sequence и не управляет очередью TX.

## Воспроизводимые программные проверки

Из `host/`, без сторонних пакетов:

```sh
python -m unittest discover -s tests -p 'test_window*.py' -v
python -m unittest discover -s tests -p 'test_wire*.py' -v
```

`tests/test_window.py` — авторские регрессии. Независимый автор владеет
`tests/test_window_conformance.py` и `tests/fixtures/window/`: отдельные
ожидаемые коды, побитовый CRC и framing, 20 синтетических полных окон через
HOST-002, повреждения/границы/повторы/отказы. Проверяются отсутствие ложного
успеха и zero-fill, точные сроки, неизменяемость, пределы до копирования,
отсутствие повторных терминальных результатов и явный reset.

Фактические команды, результаты и точный итоговый SHA должны войти в отчёт
независимого Critic-B по [quality-gate](../../docs/quality-gate.md). Наличие
тестов не заменяет их запуск. Принятие HOST-004 требует независимого PASS
не ниже 9,5/10; принятие общего протокола и аппаратные проверки остаются
отдельными условиями. Слияние принадлежит интегратору A.
