# Сегментированная запись MTREC v1

Статус: изолированный кандидат формата и синхронной библиотеки хранения;
приёмка требует независимого Critic-B на точном commit. Реализация:
`motortester/session_archive.py`. База приложения:
`db86d2247f02dbc6f770a674654f5c5bf9d92f99`. Существующие
[Capture/MTCAP v1](format-v1.md), runtime, GUI, wire 0.1 и прошивка не изменены.

## Что сохраняется и что не утверждается

`.mtrec` хранит упорядоченные полные окна, принятые части неполных окон и события
отказа до BEGIN. Для полного окна сохраняются **те же байты `.mtcap` v1**, включая
исходное представление JSON и SHA-256. `append_capture(bytes)` никогда не вызывает
повторное кодирование. `append_full(FullSegment)` отдельно кодирует переданный
неизменяемый Capture штатным v1-кодером; исходный объект остаётся тем же для
последующего локального ACK контроллером.

Это запись **сегментов**, а не непрерывная выборка от нажатия Record до Stop.
Границы каждого сегмента явные. Межоконные интервалы времени устройства неизвестны;
пропуски нельзя заполнять нулями, соединять линией или выводить из времени приёма
на ПК. Шкала полного окна остаётся номинальной, непроверенной шкалой v1. Fs и
host_elapsed_ms не доказывают физическое время искры или полное покрытие разряда.
Auto/Normal/Single здесь не реализуются и не переопределяются.

`origin`, wire-идентификаторы, принятый CONFIG и stop_evidence являются сохранёнными
заявлениями передающего кода. Хеши проверяют согласованность, не подлинность
прибора, происхождение измерения или физическую остановку. Даже `stop_ack` не
доказывает прекращение физических процессов на стенде.

## Неизменяемый API и граница контроллера

Все перечисленные снимки — frozen dataclass; нет скрытого потока, очереди,
транспорта, GUI, ожидания триггера, auto-ARM или повторного открытия на запись.
Операции spool/ZIP блокирующие: вызывать их в единственном файловом исполнителе,
отдельно от обработки Stop/COM/GUI. Объект writer не предназначен для одновременного
вызова из нескольких потоков или процессов.

1. `SessionIdentity(recording_id, session_id, origin, firmware_version,
   protocol_version, application_version)`: новый UUID записи и исходный UUID
   сеанса, заявленный источник и версии. Все шесть полей обязательны. Каждый
   полный Capture должен в точности совпасть с пятью полями источника/версий;
   `recording_id` не подменяет исходный `session_id`.
2. `SegmentProvenance(...)`: поля приведены ниже. Неизвестное передаётся как
   `None` с причиной. Библиотека не выводит недостающие сведения из похожего CONFIG.
3. `FullSegment(capture, provenance=SegmentProvenance())` удерживает точный
   исходный Capture. `SampleFragment(offset, samples)` содержит неизменяемый tuple
   исходных целых ADC-кодов. `PartialSegment(sequence, expected_samples, fragments,
   missing_ranges, reason, provenance=..., nominal_fs_hz=None,
   received_at_utc=None, deferred_checks=(), metadata_issues=())` допустим только для **известного принятого BEGIN**.
   expected_samples — объявленное BEGIN число, не последний полученный offset.
4. `AbortEvent(reason, sequence=None, provenance=...)` — событие **до BEGIN**.
   sequence сохраняется только если известен; событие не создаёт пустого окна и
   не расходует/не назначает wire window_id.
5. `SessionSpool.create(path, identity)` исключительно создаёт новый spool,
   записывает и fsync-ит заголовок. Подготовка должна успешно завершиться **до ARM**.
   Существующее имя не перезаписывается. При ошибке ARM запрещён; даже неудачно
   созданный файл остаётся для диагностики.
6. `spool.capacity` возвращает `Capacity(entries_remaining, events_remaining,
   manifest_bytes_remaining, logical_bytes_remaining, spool_bytes_remaining)`.
   `Capacity.__post_init__()` проверяет точные integer-типы и границы снимка.
   `capacity.can_reserve_windows(count=2)` — чистая консервативная проверка места
   для следующих полных/неполных окон или no-BEGIN событий сверх постоянного
   резерва завершения. `preflight_full`, `preflight_capture`, `preflight_partial`,
   `preflight_abort` проверяют конкретный элемент без записи и возвращают
   проектируемую Capacity. Это проверка, а не конкурентное резервирование места.
7. `append_full(full)`, `append_capture(v1_bytes, provenance=...)`,
   `append_partial(partial)`, `append_abort(event)` возвращают `CommitReceipt`
   **после** fsync члена, fsync индекса и чтения/проверки обоих с того же файла.
   При любой ошибке I/O writer закрывается; прежние подтверждённые данные не
   стираются. Автоматического повторного append/resume нет.
8. Receipt содержит `identity`, `entry: SegmentCommit`, `capacity_after`,
   `issuer`, `source_item`; `source_capture` возвращает исходный Capture для
   FullSegment. `spool.receipt_issuer` — отдельный непрозрачный in-process token
   для конкретного writer. `segment_digest(item)` — чистое ограниченное
   кодирование/хеширование того же полного, неполного или abort-элемента.
   `receipt.matches(identity, ordinal, issuer=token, item=exact_item,
   sha256=segment_digest(exact_item))` проверяет выдавший spool, точный объект,
   сеанс, порядковый номер и digest. Обычный конструктор/`dataclasses.replace`
   receipt не даёт подтверждения записи. Это защита от ошибки связывания внутри
   процесса, не барьер против намеренной Python-reflection.
9. Receipt подтверждает только хранение. Он **не посылает и сам не разрешает
   wire RELEASE/ACK**. Будущий контроллер отдельно сверяет свой активный token,
   точный Capture и receipt. Принятое для следующего этапа ограничение:
   matching STOP_ACK → durable append/readback receipt → локальный ACK без
   RELEASE → отдельный новый ARM. RAM-очередь или отрисовка не заменяют receipt.
   Эта библиотека не реализует и не подтверждает такой runtime-путь.
10. `finish(reason, stop_evidence='none', diagnostic='')` записывает отдельный
    завершающий кадр, fsync-ит его, закрывает writer и возвращает RecoveryReport.
    `close()` только закрывает файл и **не означает Stop**. `recover(path)`
    исключительно читает проверенный префикс и возвращает неизменяемый отчёт.
11. `finalize(report, destination, overwrite=False, cancelled=None)` повторно
    сверяет spool с отчётом, пишет архив рядом с назначением, fsync-ит, полностью
    проверяет повторным `load`, затем атомарно публикует. Метод закрытого writer
    `spool.finalize(...)` вызывает тот же путь. Перед вызовом контроллер должен
    остановить производителя и дождаться файлового исполнителя.
12. `load(path) -> SessionArchive`: проверяет все члены, но оставляет в памяти
    только метаданные, не массивы всех окон. `archive.read_segment(ordinal)`
    читает один ограниченный член и заново проверяет его по сохранённому индексу.
    Полный член декодируется прежним `recording.decode`; для частичного данные
    интерпретируются только вместе с его исходными offsets/missing_ranges.

Архивный индекс нельзя передавать как разрешение новому runtime-сеансу. Issuer и
receipt действуют только в текущем процессе; восстановление файла их не создаёт.

## Происхождение сегмента

Все поля `SegmentProvenance` обязательны в JSON, включая поля со значением null.

| Поле | Допустимое значение |
|---|---|
| generation | null или int 2…0xfffffffe; фактический ARM request_id/generation |
| config_id | null или int 1…0xfffffffe; объявленный прибором счётчик, **не CONFIG request_id** |
| acquisition_mode | null либо int 0 Auto / 1 Normal / 2 Single |
| auto_timeout_ms | null вместе с неизвестным mode; при mode0 — 100…60000, при mode1/2 — 0 |
| host_elapsed_ms | null либо int 0…2^64−1, заявленное монотонное время хоста; известные значения не убывают |
| wire_version | null либо строка `0.1` |
| start_operation | null либо строка `arm`; type8/software-immediate не добавлен |
| wire_session_nonce | null либо int 1…2^64−1; для полного Capture должен совпасть с целым значением его UUID |
| config_payload_hex | null либо 32 lowercase hex-символа: точные 16 байт принятого CONFIG payload `<HBBBBHHHI>` |
| begin_request_id / terminal_request_id | null либо int 0: unsolicited BEGIN/END/ABORT wire 0.1 |
| begin_sequence / terminal_sequence | null либо int 1…0xfffffffe; при наличии обоих terminal > begin |
| terminal_kind | null, `end` или `abort` |
| end_samples_crc32 | null либо uint32; при наличии terminal_kind обязан быть `end` |
| abort_reason_code | null либо int1…6, только при terminal_kind=`abort`; исходный числовой ABORT reason |
| unavailable_reason | строка1…1024 символа, если применимое поле выше неизвестно; иначе null |

У END поле abort_reason_code=null неприменимо; у ABORT поле end_samples_crc32=null
неприменимо. Эти два случая не требуют выдумывать отсутствующий факт.

Значение по умолчанию `not_supplied` описывает отсутствие сведений у отдельного
офлайн-входа; live-контроллер обязан передавать доступные факты и точную причину
неприменимых/отсутствующих полей. Неизвестное не становится нулём. Полный Capture
не может иметь terminal_kind=abort. Известный END CRC полного окна проверяется
по исходным uint16-le кодам. У partial такой CRC может документировать неудачу и
не превращает запись в полную. No-BEGIN событие не может содержать BEGIN IDs.

CONFIG сохраняется отдельно от MTCAP, без изменения v1. Проверяются профиль1,
поля mode/source/edge, нулевые reserved, уровень1…4094, pre0/512/1024 и
согласованность mode/timeout. Для полного окна также сверяются уровень, фронт,
предыстория и источник запуска. При наличии CONFIG profile1 требуется2048 отсчётов
и номинальная Fs50000; для partial — expected_samples2048, Fs50000 либо null.
При известном wire0.1 window sequence1…0xfffffffe; известный nonce любого вида
записи совпадает с session_id. Офлайн-вход с неизвестным CONFIG сохраняет общие
пределы v1. Отсутствие ошибки здесь не заменяет проверку
CAPS/принятия CONFIG или физическую проверку прибора.

## ZIP-профиль MTREC v1

Расширение `.mtrec`. Все члены ZIP_STORED, без шифрования, сжатия, ZIP64,
многотомности, extra fields, комментариев, data descriptors, directory/symlink/
special entries. Версии create/extract — 20, create_system — 3,
external_attr — `0o100600 << 16`. Имена ASCII; flags=0. Профиль намеренно уже
произвольного ZIP: перепаковка сторонним архиватором может быть отклонена.

Порядок членов строго такой, локальные заголовки следуют подряд с offset0,
центральный каталог непосредственно за последним членом, EOCD — последние22 байта.
internal_attr=0; прочие поддерживаемые атрибуты перечислены выше:

- `manifest.json`
- `segments/00000000.mtcap` для полного окна, `.u16le` для частичного или `.json`
  для no-BEGIN abort; сквозной ordinal0…N−1
- `diagnostics.json`

Никакие пути из архива не извлекаются на файловую систему. Неизвестные имена,
дубликаты, NUL, `..`, backslash, абсолютные/drive пути отвергаются. До создания
ZipFile ограничиваются размер файла и размер центрального каталога. Затем каталог
потоково обходится по фактическим46-байтовым заголовкам: проверяются фактическое
число записей, совпадение с EOCD, ограниченные имена и их уникальность, признаки
формата, размеры payload и их сумма. Недоверенный count из EOCD не заменяет этот
проход. Вспомогательный набор имён содержит не более32770 строк байтов по32 байта;
общий ZipInfo-массив до успешного прохода не создаётся.
После разбора сверяются локальные и центральные имена, CRC, размеры/offsets и
точная укладка; перед чтением каждого payload проверяется его размер.

JSON — UTF-8 без BOM, объект верхнего уровня. До `json.loads` выполняется
лексический проход без дерева значений: глубина≤16; узлов≤3145728 (контейнер или
скаляр — один узел, ключи не узлы); полей одного объекта≤32; ключ≤64 символов;
строковое значение≤65536 Unicode-символов; числовой токен≤64 байт. UTF-8 и
экранированные surrogate pairs считаются по символам, а не по числу байтов.
Сырой строковый токен дополнительно ограничен12×число_символов+2 байтами.
Обход держит только стек глубины≤16 и декодирует по одному короткому ключу;
полные контейнеры и значения до прохождения лимитов не декодируются.

Независимые лимиты массивов тоже проверяются до общего декодера: segments≤32768,
fragments≤1024, missing_ranges≤1025, каждая пара offset/count или start/end≤2,
deferred_checks/metadata_issues≤16, recovery_issues≤1. Общий лимит неизвестного
массива —32768; неизвестность схемы впоследствии всё равно вызывает отказ.
Структурный проход не заменяет проверку схемы, точных типов и дубликатов.
Неизвестные,
отсутствующие и повторные поля запрещены; NaN/Infinity запрещены. Integer поля
не принимают bool/float/строку. Текст не содержит управляющих кодов U+0000…001F,
суррогатов и U+FFFE/U+FFFF. SHA-256 — 64 lowercase hex-символа.

### manifest.json

Точные поля:

- `format: "motortester-session"`, `format_version: 1`, `capture_format: "mtcap-v1"`
- `coverage: "segmented"`, `time_basis: "per_segment_nominal_unverified"`,
  `intersegment_device_gap: "unknown"`
- `identity`: шесть полей SessionIdentity
- `termination`: только `reason` и `stop_evidence`
- `segment_count`: число всех capture/partial/abort записей
- `segments`: упорядоченный массив дескрипторов ниже
- `diagnostics`: точные `byte_count` и `sha256` файла diagnostics.json

Дескриптор `SegmentCommit`: `ordinal`, `kind` (`capture`/`partial`/`abort`),
`byte_count`, `sha256`, `sequence`, `sample_count`, `provenance`, `partial`,
`abort_reason`. Имя члена однозначно определяется ordinal/kind. Для полных и
частичных окон sequence — исходный uint32; он строго растёт между окнами одного
сеанса. Разрывы сохраняются, потерянные окна не выдумываются. Abort sequence может
быть null или известным uint32; он не меняет последовательность окон.

У capture `partial` и `abort_reason` равны null; sample_count — 1…65536 и должен
совпасть с неизменённым MTCAP. Его session_id/origin/версии совпадают с identity.

У partial `abort_reason=null`, sample_count — число **принятых** кодов0…65536.
`partial` имеет точные поля `expected_samples`, `fragments`, `missing_ranges`,
`reason`, `nominal_fs_hz`, `received_at_utc`, `deferred_checks`, `metadata_issues`.
Последние два массива сохраняют исходные аннотации WindowResult: каждый ≤16
непустых строк по128 символов, без объявления неуспешной проверки успешной. fragments — массив пар [offset,count]
в возрастающем порядке без перекрытия; каждый count>0 и диапазон внутри
[0,expected_samples), expected_samples1…65536. `.u16le` содержит подряд только
реально переданные коды в указанном порядке; их исходные offsets не теряются.
Каждый код — uint16-le0…4095. missing_ranges — **точное дополнение** диапазонов,
пары [start,end) включая начальный/внутренний/конечный пробел. BEGIN без DATA:
пустой member, fragments=[], missing_ranges=[[0,N]]. Нулевое число пропусков
тоже не повышает partial до capture: END/CRC могли не пройти проверку.
Fs=null либо конечное число1…1000000; UTC=null либо метка1…64 символа с offset0.

У abort `sample_count=null`, `partial=null`, `abort_reason` — непустая причина.
Его JSON-член содержит ровно `kind:"no_begin_abort"`, `reason`, `sequence`,
`provenance`; значения должны совпасть с индексом. Это событие, не окно отсчётов.

### Завершение и диагностика

reason: `user_stop`, `single_complete`, `error`, `capacity`, `recovered`.
stop_evidence: `none`, `stop_ack`, `single_release_ack`, `unknown`.
`single_release_ack` допустим только с `single_complete`; такой сеанс содержит
ровно один capture. `recovered` требует `unknown`. Отсутствие stop_ack никогда
не заменяется предположением. Успешный файл не означает успешную остановку.

diagnostics.json содержит ровно `format_version:1`, `message` и `recovery_issues`.
message — строка0…65536 символов. recovery_issues — не более одной причины,
поскольку восстановление останавливается на первом неверном хвосте; её поля
`kind`, `offset`, `byte_count` описывают исходный spool, а не адреса ZIP.
kind: `missing_finish` (byte_count=0), `uncommitted_tail` (неподтверждённая пара,
включая orphan/обрезанный член или индекс), `invalid_terminal_or_tail`.
Наличие проблемы требует reason=recovered. Сырой непроверенный хвост остаётся
в spool; он не выдаётся за принятые ADC-коды.

### Причина восстановления во время Record

Host сохраняет первую причину перехода в RECOVERY в существующей строке
`SessionOutcome.diagnostic` / `diagnostics.json.message`. Схема MTREC v1, spool,
wire и сроки ожидания не меняются. `SessionController` до сброса pending-команд
создаёт один неизменяемый `RecoveryDiagnostic`; он остаётся в событии и снимке
до нового сеанса. Снимок позволяет не потерять причину и при исключении,
прервавшем доставку событий. Поля строятся только из ограниченных enum и uint32:

- `reason`: код RECOVERY, например TIMEOUT, UNKNOWN_WRITE, TRANSPORT_LOST,
  PROTOCOL_FAULT; `fault`: VERSION / DECODE / DOWNSTREAM либо `none`.
- `command` и `request_id`: именно просроченный запрос для TIMEOUT либо запрос
  текущего TxTicket для UNKNOWN_WRITE. При неизвестной связи с конкретной
  командой — `none` и 0; pending-запрос не объявляется причиной ошибки чтения.
- `pending`: вид и ID обычного запроса, `stop_request_id`: ID ожидающего STOP.
  Если оба запроса присутствуют, контекст обоих сохраняется отдельно от
  конкретного запроса, выбранного существующей проверкой срока ожидания.

Получаемый текст `RECOVERY reason=…; fault=…; command=…; request_id=…;
pending=…/…; stop_request_id=…` короче 256 ASCII-символов. В него не попадают
backend-исключения, произвольные сообщения прибора, имена COM-портов, пути,
payload или credentials. Это наблюдение host, **не диагноз причины сбоя платы**.

Контроллер записи сохраняет этот текст отдельно от прежнего первого `fault`.
Если до RECOVERY уже был отказ хранения/контроллера, он остаётся первым fault,
а подробности восстановления дописываются отдельно. Повторные события, Stop,
проверки состояния и ошибки Save не заменяют исходную причину. Новый Record
и новый nonce очищают старую диагностику; поздние callbacks/чужой token её не
переносят. Изменение диагностики входит в прежнюю проверку актуальности
FINALIZE_READY: захваченный устаревший finish остаётся неподтверждённым.

Панель записи и сообщение успешного Save сохраняют подробности; новое окно
просмотра показывает их из `.mtrec` даже без состояния старого соединения.
Успешный Save подтверждает публикацию файла, но не исправление захвата и не
Stop. До BEGIN допустим архив без сегментов; уже принятые части/полные окна
сохраняются без дополнения отсчётов. Архивы прежней версии с пустой диагностикой
или `transport_recovery` по-прежнему открываются; утраченную ранее причину из них
восстановить нельзя. Проверки: `tests/test_recovery_details.py` и recovery-сценарии
`tests/test_gui_recording.py`, normal и `python -O`, плюс прежние проверки
финализации, Stop, runtime и строгого архивного формата. Синтетический Linux/Qt
прогон не подтверждает работу на Windows 10 или с физическим USB/платой.

## Spool v1 и границы сбоя

Один append-only файл, исключительно создаваемый режимом `x+b`. Magic:
`4d 54 53 50 00 01 00 00`. Затем HDR1: `<4sI>` с длиной UTF-8 JSON,
JSON и 32 байта SHA-256 JSON. Заголовок имеет ровно `format:"motortester-spool"`,
`format_version:1`, `identity`.

Каждая пара состоит из:

1. MEM1 `<4sI>` + исходный payload; flush/fsync.
2. IDX1 `<4sI>` + JSON того же SegmentCommit + 32 байта SHA-256 JSON; flush/fsync.
3. Повторное чтение обеих записей, хеша и семантическая проверка; только затем receipt.

END1 имеет тот же формат с SHA-256 и JSON `reason`, `stop_evidence`, `diagnostic`.
Никаких данных после END1 не допускается. На восстановлении проверяются версия,
identity, каждая пара, порядок, ресурсы и содержимое. Только полностью проверенная
пара становится записью. После первого неверного места поиск «следующего хорошего»
кадра запрещён. Неверный заголовок не позволяет определить сеанс и даёт отказ.

Нет END1/END1 оборван/повреждён/имеет хвост: recovered/unknown, даже если ранее
виден текст user_stop. Полный достоверный END1 сохраняет его исходное заявление.
При исключении после записи, но до возврата receipt, восстановление иногда может
найти ещё одну целую пару: это не означает, что вызывавший код получил разрешение
ACK. Не завершённые RAM-объекты и не переданные прибором отсчёты не гарантируются.

## Лимиты, резерв и память

Это защитные лимиты ПО, не характеристики STM32, диска или времени измерения:

- 256 MiB — сумма payload всех ZIP-членов; отдельно 256 MiB — физический spool
- 32768 — суммарно capture/partial/abort; из них abort ≤4096
- 8 MiB manifest; 1 MiB diagnostics/END1; 16 KiB header и отдельный abort JSON
- 64 KiB один индекс; ≤1024 фрагмента и ≤1025 missing ranges в partial
- полный MTCAP ≤147504 байт по v1; partial ≤131072 байта
- постоянный резерв завершения — 1 MiB +16 KiB; отдельный16 KiB запас внутри
  manifest покрывает фиксированные поля/пунктуацию

При admission считаются точные payload и сериализованный индекс+1 байт-разделитель.
Прогноз spool учитывает обе8-байтовые рамки и32-байтовый digest индекса. Должны
одновременно помещаться spool+резерв, payload+индексы+резерв, лимит manifest и
счётчики. Лимит метаданных может сработать раньше лимита32768. После отказа
приёма обычного элемента резерв позволяет записать окончательную диагностику.

`can_reserve_windows(n)` дополнительно консервативно требует n слотов событий,
n×(65536+1) байт индекса, n×(147504+65536+1) логических байт и
n×(147504+65536+48) spool-байт. Это максимум для одного полного/частичного окна
или ограниченного abort; никаких free-space обещаний метод не даёт.

Физический ZIP ограничен `256 MiB + (32768+2)×(76+2×32)+22` байт: заголовки
не отменяют256 MiB логический предел. Центральный каталог ограничен
`(32768+2)×(46+32)` байт **до его выделения ZipFile**; фактические записи также проходят отдельный
потоковый допуск до создания ZipInfo. Чтение обрабатывает один
ограниченный payload за раз; Python-объекты метаданных имеют дополнительный
ограниченный, но не равный размеру JSON расход памяти. Массивы всех Capture не
накапливаются. Рост счётчиков/проверка порядка при append линейны по числу записей
в целом, без повторного сканирования всего индекса на каждом окне.

Числовой лимит64 байта покрывает штатные uint64 и JSON-представления Python float.
32 поля покрывают крупнейший объект текущей схемы с запасом; ключи фиксированы и
короче64 символов. Узловой бюджет3×1024×1024 выбран отдельно от байтового лимита:
он отсекает плотные произвольные деревья, сохраняя допустимую плотную структуру
частичных записей у8 MiB границы (1024 соседних одноотсчётных фрагмента на окно).
Тест проверяет этот предельный структурный проход с sentinel вместо выделения
его большого Python-дерева. Это не обещание малого RSS: фактическая память
разрешённых метаданных включает Python-объекты сверх размера JSON. Измерение
защитного отказа на400000 полей отдельно исключает заранее созданные байты
fixture и не выдаётся за максимум RSS всего приложения.

## Сохранение, отмена и ограничения файловой системы

Временный ZIP находится на том же filesystem, что destination. До публикации
сбой записи, fsync, повторного открытия, проверки, отказ замены или отмена
сохраняют старый destination и spool. По умолчанию `os.link` не заменяет уже
существующее имя, включая появившееся во время сохранения; `overwrite=True`
использует `os.replace`. Назначение не может совпасть со spool или его hardlink.
Файл spool не удаляется даже после успеха.

cancelled — необязательный callable; проверяется до начала, между сегментами и
перед публикацией. После атомарной публикации отмена уже не может вернуть старый
файл. Последующая неудача удаления временного hardlink не объявляется неудачей
замены: возможен лишний временный файл, опубликованная запись остаётся целой.
Сбой процесса во время сохранения может оставить временный ZIP; исходный spool
сохраняется. Нужно место для второго полного файла; проверка свободного места
не предотвращает одновременное исчерпание диска другим процессом.

Гарантируется успешный вызов OS fsync и чтение байтов с файла; не гарантируются
переживание потери питания, поведение всех контроллеров диска, сетевых/съёмных
filesystem, сохранение directory entry после аварии ОС. Эти границы требуют
отдельной проверки Windows/NTFS и аппаратуры. Здесь выполнены только синтетические
Linux-проверки, включая реальные subprocess exits, повреждения и инъекции отказов.

## Воспроизводимые проверки

Из `host/`, сторонних пакетов не нужно:

```text
python -m unittest discover -s tests -p test_session_archive.py -v
python -O -m unittest discover -s tests -p test_session_archive.py -v
python -m unittest discover -s tests -p test_recording.py -v
python -O -m unittest discover -s tests -p test_recording.py -v
```

Проверки включают ≥3 окна с байтовым сравнением, partial с ведущим/внутренним/
конечным пропуском, zero-DATA и no-BEGIN, строгие схемы/версии/identity/provenance,
поддельные ZIP/пути/CRC/SHA, scalar/string/node/object/array guards до общего
JSON-декодера, реальный count и признаки каталога до ZipInfo, лимиты до дорогого
чтения, обрезание каждого байта
spool, выход процесса на границах записи/fsync, ошибку readback, отказ/отмену
сохранения и сохранность прежнего файла. Точный SHA и логи проверки передаются
в отдельном отчёте ревью. Эти проверки не закрывают GUI, runtime-интеграцию,
чистую Windows10, USB, непрерывный захват, физический Stop или целый разряд.
