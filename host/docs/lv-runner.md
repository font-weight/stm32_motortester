# Последовательная серия LV-001 без Qt

Это отдельная **программная основа**, проверяемая только на синтетическом
байтовом эмуляторе. Один явный запрос запускает одно прогревочное окно и
20 запланированных основных попыток. Ошибка не заменяется новой попыткой.
Физический вход остаётся закрытым: ни имя COM-порта, ни согласие общего вида,
ни успешный HELLO не разрешают подключение платы.

Основание исходников: PR158, commit
`1930f75b976be17a3df51da079b6d8ba275e3f73`, tree
`c92973b11fbdf31e43bd8d709e20a4a1a03a9f62`.
В этой итерации добавлены только `motortester/lv_runner.py`, его тесты и этот
документ. Существующие collector, transport, runtime, wire, GUI, launcher,
форматы файлов, спецификация упаковки и CI не изменены. Сам факт наличия
документа не означает независимую приёмку кандидата.

## Что выполняет один запрос

1. Проверяет параметры и новую выходную папку. Старая, даже пустая папка
   не используется. Отдельный рабочий поток создаёт исходный индекс.
2. Открывает только встроенный программный byte-peer через существующий
   `SerialTransport`. В этом маршруте нет реального устройства, сканирования
   портов, фабрики от пользователя или автоматического выбора порта.
3. Согласует CAPS и настройки существующим collector: Auto, profile 1,
   source 0, pretrigger 0. Пользователь явно выбирает фронт 0/1, уровень
   1…4094 кодов и конечный Auto timeout 100…60000 мс.
4. Перед каждым ARM сохраняет намерение именно этой попытки в индексе.
   Затем передаёт настоящие COBS/CRC байты через существующий runtime.
5. После проверенного полного окна немедленно ставит Stop, обслуживает обмен
   до подходящего STOP_ACK и снятия барьеров. Между END и постановкой Stop
   нет файловой операции. Во время активного окна runner не проверяет папку
   через файловую систему и не сохраняет массивы на диск.
6. Через неизменный `persist_attempt()` сохраняет `.mtcap`, sidecar и индекс,
   повторно читает их и проверяет точное соответствие. Только collector
   выполняет локальный ACK **того же** исходного объекта Capture.
7. Следующий ARM возможен только после этого возврата, при живом и здоровом
   запросе. RELEASE, повтор команд, переподключение, reset и замена неудачного
   окна отсутствуют. Прогрев учитывается отдельно от основных 20 попыток.

Auto timeout сохраняет `trigger_kind=auto_timeout` без выдуманного события.
Если эмулятор выдаёт настоящее для своей модели пересечение, сохраняются
его исходные trigger index, edge и level. Шкала времени остаётся номинальной
и непроверенной, единица амплитуды — код АЦП; синтетика не становится измерением.

## API для будущего caller

Из `host/`, без Qt, pyserial и сторонних пакетов:

```python
from motortester.lv_collector import RunIdentity
from motortester.lv_runner import RunRequest, run_synthetic
from motortester.session import Config

request = RunRequest(
    directory="новый опыт LV-001",
    identity=RunIdentity(
        origin="simulator",
        application_commit=exact_application_commit,
        application_tree=exact_application_tree,
    ),
    config=Config(profile=1, mode=0, source=0, pretrigger_samples=0,
                  edge=0, level_code=2048, auto_timeout_ms=100),
)
handle = run_synthetic(request)
result = handle.wait(100)  # Наблюдение максимум 100 мс, не отмена.
# handle.snapshot(): немедленный неизменяемый снимок без I/O.
# handle.stop(): постоянный запрет новых ARM; не ждёт диск/транспорт.
# handle.retire(250): Stop + ограниченное ожидание владельца.
```

`RunRequest` не принимает количество окон, реальный порт, transport factory,
общий флаг допуска или часы от caller. Часы runner и byte-peer:
`time.monotonic_ns() // 1_000_000`. Запрос копируется перед передачей рабочему
потоку; последующая правка исходного объекта не меняет начатую серию.

Commit и tree приложения обязательны, ровно по 40 шестнадцатеричных знаков;
`TBD` в этих двух полях не принимается. Это **явно переданные сведения** о
запускаемом исходном снимке, а не автоматическая проверка истинности сборки.
Не передавайте SHA базового PR158 вместо SHA нового кандидата с runner.
Если checkout изменён, сначала зафиксируйте его отдельный точный источник
и хеши; чужой чистый commit не описывает незакоммиченные изменения.

Старые provenance pins внутри collector/MTCAP не переписаны: они обозначают
происхождение существующих модулей. Текущая identity хранится отдельно в
индексе и sidecar. Неизвестные аппаратные сведения остаются `TBD` и ничего
не разрешают. Хеши устанавливают связь артефактов, а не физическую истину.

## Stop, сроки и блокирующий диск

Collector, runtime и serial имеют **одного владельца** от начала до закрытия.
Caller читает только неизменяемый `RunSnapshot` и выставляет постоянный запрет
продолжения. Во время `fsync`, чтения или закрытия портов caller не вызывает
`collector.cancel()` параллельно рабочему потоку. Очереди из 20 массивов и
отдельного потока записи нет.

Обычной проверки отмены перед `arm_next()` недостаточно: неизменный collector
сначала пишет индекс, затем ставит ARM. Поэтому небольшой транспортный
адаптер проверяет запрет непосредственно перед допуском очередного вызова
backend. Он использует существующий codec только для распознавания одного
целого исходящего кадра и его точного оставшегося суффикса. Нового протокола,
самостоятельного сопоставления ACK и другой политики сеанса он не вводит.

Короткая проверка под lock является моментом допуска записи. Lock никогда
не удерживается во время I/O. Если вызов backend уже допущен, он может
завершиться после Stop: отмена этого вызова не обещается. После запрета ни
новый ARM, ни оставшийся суффикс частично переданного ARM не допускаются.
Stop не вставляется внутрь такого суффикса. В этом случае исходный runtime
переходит в recovery, а подтверждённый физический Stop не заявляется.
Подходящий Stop в неповреждённом потоке можно закончить в пределах отдельного
короткого бюджета завершения обмена.

Если отмена пришла внутри `persist_attempt()`, рабочий поток сохраняет
владение. Метод может позже закончить точную запись и локальный ACK после
ранее подтверждённого Stop. Это допустимое завершение уже начатого
сохранения, но оно никогда не снимает запрет runner и не разрешает следующий
ARM. Даже если последний collector индекс стал `sealed_unverified`, живой
runner после отмены не возвращает `COMPLETE`.

Фиксированные верхние границы `Limits`:

| Поле | По умолчанию | Максимум |
|---|---:|---:|
| `run_ms`, весь запрос | 1 800 000 мс | 3 600 000 мс |
| `attempt_ms`, от допуска намерения до возврата сохранения | 90 000 мс | 120 000 мс |
| `storage_ms`, одна файловая стадия | 10 000 мс | 30 000 мс |
| `shutdown_ms`, обмен после постоянного запрета | 1 000 мс | 1 000 мс |
| `poll_ms`, пауза между итерациями | 2 мс | 20 мс |

Каждое поле — строго целое положительное число; bool/float не принимаются.
Прочие операции имеют бюджет 1000 мс. Настройки SerialTransport: read timeout
0,01 с, write timeout 0,05 с. Сроки команд/прогресса исходного runtime не
сбрасываются и не продлеваются. Его часы читаются и после I/O. Runner
проверяет свои сроки до/после стадий и на границе допуска транспортных
операций; для запрета позднего ARM вызовы `snapshot()`/`wait()` не нужны.

Эти бюджеты ограничивают допуск и время ожидания caller, но не гарантируют
срок завершения зависшего системного вызова. При таком вызове `stop()` и
`snapshot()` остаются доступны, а `wait()` ждёт не более запрошенных
0…1000 мс. ОС или Python-поток принудительно не прерываются.

В модуле допускается не более одного живого owner thread. Незавершённый
владелец, включая зависший `close()`, удерживается модулем; новый запуск
отклоняется, пока фактический `thread.is_alive()` не стал false. Это
ограничение процесса, не блокировка всех независимых процессов компьютера.

## Как читать результат

- `RUNNING`: владелец ещё работает, постоянного запрета пока нет.
- `PENDING`: запрет уже установлен, но владелец остаётся живым. Запись,
  чтение или закрытие могут ещё выполняться; никаких обещаний join/close нет.
- `CANCELLED`: владелец закончился после Stop caller или сигнала.
- `FAILED`: ошибка/срок/неподтверждённое закрытие; новая попытка не подставляется.
- `COMPLETE`: этот живой запуск наблюдал проверенное сохранение прогрева и
  всех 20 попыток, завершение collector, успешное закрытие и окончание потока
  без отмены/истечения срока. Это исключительно программный результат.

`operation`, `collector_state`, `collector_reason`, `storage_status`,
`writer_operation`, `writer_settlement`, `retained_capture` и `retained_fragments` относятся к
последнему наблюдению владельца (`observed_at_ms`). Внутреннее состояние
заблокированного метода caller не читает. `matched_stops` — счётчик принятых
Stop; `last_stop_generation` относится только к указанному поколению.
Сравнивайте его с `current_arm_request_id`, а не объявляйте новый ARM
остановленным на основании Stop предыдущей попытки. `current_generation`
меняется только после принятого ARM_ACK, поэтому при неизвестном исходе
записи ARM может всё ещё относиться к предыдущему окну.
`writer_operation` указывает последнюю файловую команду START/ARM_INTENT/PERSIST;
ENTERED означает вход в эту команду, RETURNED_VERIFIED — наблюдённый возврат
после её проверок, RAISED_UNCONFIRMED — исключение. Это не утверждение о
моменте входа/выхода отдельного системного вызова и не подтверждение всей серии.

`directory` всегда означает запрошенный путь. `folder_created` становится
true только после наблюдения успешного создания и проверки папки. При
блокировке первоначального индекса папка может фактически уже существовать,
но runner ещё не заявляет её подтверждённой. `transport_closed` становится
true только после возврата успешного `close()` и наблюдения CLOSED.
`physical_verified` всегда false; matching STOP_ACK также не доказывает
физическую безопасность, точность АЦП или полноту разряда.

Сохраните handle при PENDING: исходный владелец и его единственный результат
остаются живы. Не начинайте другую серию «вместо зависшей». При остановке
самого процесса сведения в памяти могут быть потеряны. Отдельного нового
формата lifecycle-файла нет; факт отмены runner во время последнего сохранения
не обещается восстановить после потери процесса. Проверка существующей папки
через `motortester.lv_collector` всегда оставляет `prior_writer_outcome=UNKNOWN`.
Целостность восстановленных файлов не превращает прошлый отменённый запуск
в успешно завершившийся и не доказывает его локальный ACK.

После **фактического окончания потока** `handle.retained_evidence()` позволяет
прочитать удержанный текущий Capture или неполный WindowResult и отдельные
ограниченные копии индекса/байтового журнала в JSON bytes. Во время записи
или закрытия метод отклоняется, не читая состояние владельца. Если collector
вообще не создавался, возвращается None. Эти данные находятся в памяти,
`durable=false`: метод ничего не пишет, не подтверждает, не повторяет и не
восстанавливает. Возвращаемые массивы/фрагменты неизменяемы, JSON bytes
отделены от внутренних структур; полного буфера прежних 20 окон нет.
Отдельные пределы копий — 65 536 байт для индекса и 2 MiB для журнала.

## Файлы, пределы и восстановление

Сохраняются прежние `index.json`, `attempt-00.json`/`.mtcap` для прогрева и
`attempt-01`…`attempt-20` для основной серии. Форматы, SHA-связи и правила
повторного чтения описаны в [lv-collector.md](lv-collector.md). Неполные
массивы остаются фрагментами с missing ranges; отсутствие BEGIN, дубликаты,
исходные ошибочные байты, CRC и неопределённый объём записи не скрываются.
Данные предыдущей попытки не удаляются и не заменяются.

Пределы runner: путь не более 1024 символов/64 компонентов, 21 попытка,
44 файла с учётом одной временной записи, суммарный консервативный потолок
49 300 464 байта. Для обычного успеха ожидаются 43 файла. MTCAP ограничен
147 504 байтами, sidecar — 2 MiB, индекс — 65 536 байтами. Это верхние
границы форматов, а не ожидаемый размер одного окна из 2048 отсчётов.
Совокупный наблюдаемый транспорт ограничен 2 752 512 байтами и 2 000 000
вызовами; сохраняются прежние меньшие лимиты журнала одной попытки.
Задержанная файловая стадия не создаёт очередь следующих окон.

Имеющиеся пути, symlink/reparse-компоненты, специальные имена Windows,
потоки `name:stream`, управляющие символы и выход за пределы отклоняются.
Идентичность родителей/папки и размеры/типы выходов проверяются на файловых
границах; Unicode и внутренние пробелы разрешены. Проверки не являются
песочницей против враждебной подмены файловых путей во время системного
вызова: существующий collector использует path-based I/O. Папка должна
принадлежать этому запуску и не редактироваться параллельно. Обнаруженная
подмена или stale index прекращает серию; чужой индекс не исправляется.

Используется неизменный `recording.atomic_write`: flush/fsync файла,
атомарная публикация и точное повторное чтение. Гарантия сохранения записи
каталога при внезапной потере питания отдельно не проверена; runner не
усиливает гарантии файловой системы обещаниями. Disk full, испорченное
повторное чтение или исключение оставляют доступные файлы и удерживаемый
Capture/фрагменты; автоматической повторной записи нет.

## Синтетическая команда и сигналы

Из чистого checkout **именно проверяемого кандидата**, из `host/`:

```sh
python -m motortester.lv_runner "новый опыт" \
  --application-commit "<точный commit кандидата>" \
  --application-tree "<точное tree кандидата>" \
  --edge 0 --level 2048 --timeout-ms 100
```

Подставьте реальные SHA, не строки в угловых скобках. Команда использует
только встроенный byte-peer, не реальный COM. Код выхода 0 означает
наблюдённый программный COMPLETE; любой незавершённый/отменённый/неудачный
исход даёт 2. Только CLI временно устанавливает обработчики SIGINT/SIGTERM
и восстанавливает прежние. Импорт/библиотека не меняют обработчики приложения.
Caller может связать свой обработчик с `handle.signal_stop()`; этот метод
лишь устанавливает постоянный флаг без lock/I/O. Ctrl-C не подтверждает
отмену уже вошедшего в ОС вызова. Если CLI выходит с PENDING, окончание
записи/закрытия не подтверждено; сохраните всю папку и проверяйте её отдельно.

## Отдельные открытые этапы

`run_device(*args, **kwargs)` безусловно выдаёт AdmissionError **до**
рассмотрения аргументов, создания serial, перечисления или открытия портов.
Не предусмотрено отключение этой защиты общим флагом. Нужен согласованный
и независимо проверенный интерфейс допуска A: паспорт конкретной платы,
подключение/питание/земля, точный образ и board-config, native USB identity,
допустимый измеренный вход и происхождение измерений. Ни такой реальный
bundle, ни его физическая истинность здесь не устанавливаются.

Связь с frozen launcher/GUI, упаковка новой версии, актуальный source-key
inspector/checker, выполнение на Windows, реальные USB/АЦП и физический
LV-001 — отдельные этапы. Старые PR158/159, Windows-артефакты и их оценки
не принимаются за свидетельство проверки нового runner.

Авторские проверки из `host/`:

```sh
python -m unittest discover -s tests -p test_lv_runner.py -v
python -O -m unittest discover -s tests -p test_lv_runner.py -v
QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -v
```

Последняя команда требует уже установленных закреплённых GUI-зависимостей.
Результаты тестов и независимый вердикт должны относиться к точному новому
commit/tree и хешам трёх файлов. Linux/offscreen, модели ошибок диска и
эмулятор подтверждают только соответствующие программные свойства.
