# HOST-009: ограниченный последовательный транспорт ПК

Задача: [issue #49](https://github.com/font-weight/stm32_motortester/issues/49).
База: `bd58245ecf64f08dcfe6d6fec3981e26fd7ff0ed`.
Область: `motortester/transport.py`, `tests/test_transport.py` и этот документ.
Это отдельный программный компонент для будущего подключения контроллера,
часть MVP-U02/U07/U10. Он не подтверждает выполнение этих требований целиком.
Приёмка компонента требует независимого Critic-B по
[quality-gate.md](../../docs/quality-gate.md), с оценкой не ниже 9,5/10.

## Назначение и границы

`SerialTransport` выполняет ограниченные байтовые операции с явно выбранным
последовательным портом. Модуль не знает framing, команд, ACK, окон и состояния
прибора. Он не сканирует порты, не выбирает первое найденное устройство,
не подключается при импорте/создании объекта, не переподключается и не повторяет
запись автоматически. URL-транспорты `loop://`, `socket://` и подобные запрещены.

Все вызовы, включая создание объекта, открытие, чтение, запись и закрытие,
должны принадлежать одному рабочему потоку захвата. В будущем GUI передаёт
ему запросы; GUI-поток не выполняет этот I/O. Экземпляр и backend нельзя
разделять между потоками или вызывать повторно из backend. Здесь нет Qt,
фонового потока, блокировок, очередей, таймера и диспетчера событий.
Организация рабочего потока и его остановки остаётся задачей интеграции.

Ограничение 4096 байт относится к одной операции на границе адаптера, а не
к размеру окна или USB-пакета. Непустой вызов делает ровно один `read` либо
`write` backend; внутренних циклов дозаписи/дочитывания у адаптера нет.
Сам pyserial может выполнять несколько системных вызовов внутри одной операции.

## Публичный интерфейс

- `SerialTransport(backend_factory=None)` создаёт закрытый объект.
  `None` выбирает лениво загружаемый `serial.Serial`. При отсутствии pyserial
  только явный `open` получает `TransportOpenError` с объяснением зависимости.
- `open(port, *, baudrate=115200, read_timeout=0.05, write_timeout=0.1)`
  открывает только переданное имя. Перед созданием backend проверяются все
  аргументы. Передача `port=None` в конструктор backend исключает неявное
  открытие; затем устанавливается выбранное имя и явно вызывается `open()`.
- `read(size=4096)` возвращает неизменяемые `bytes`, длиной от 0 до `size`.
- `write(data)` возвращает точное целое число известного принятого префикса
  от 0 до длины переданного буфера.
- `close()` делает одну попытку закрытия. После подтверждённого закрытия
  повторный `close()` ничего не делает.
- Свойства только для чтения: `state` (`CLOSED`, `OPEN`, `RECOVERY`) и `port`
  (выбранное имя либо `None` после подтверждённого закрытия).

Допустимые аргументы:

| Аргумент | Ограничение адаптера |
|---|---|
| `port` | Точный тип `str`, от 1 до 1024 символов; без пробелов по краям, управляющих ASCII-символов и `://` |
| `baudrate` | Точный тип `int`, 1…4294967295; поддержка конкретного значения проверяется backend при открытии |
| `read_timeout` | Точный `int` или `float`, конечное число 0…1 с; 0 означает опрос без ожидания |
| `write_timeout` | Точный `int` или `float`, конечное число больше 0 и не больше 1 с |
| `size` | Точный тип `int`, 0…4096 |
| `data` | Точные типы `bytes`, `bytearray` либо одномерный непрерывный `memoryview` с размером элемента 1 байт; 0…4096 байт |

`bool`, подклассы чисел/строк/байтов, `None`, NaN, бесконечность и неявное
преобразование произвольных объектов не допускаются. Типы и границы проверяются
обычными условиями, не `assert`; контракт сохраняется при `python -O`.
Некорректный аргумент вызывает `TransportArgumentError`, не меняет состояние
и не обращается к backend. Проверка аргументов предшествует проверке состояния.
Освобождённые, многомерные, непрерывно не расположенные и многобайтные представления
памяти отклоняются. Размер проверяется до копирования. Допустимый изменяемый
буфер копируется в `bytes` перед записью; backend не получает исходный буфер.
Владелец не должен менять/освобождать буфер одновременно с вызовом.

Нулевой размер чтения и пустая запись в состоянии `OPEN` возвращают `b''`
и `0` без backend-вызова. В `CLOSED`/`RECOVERY` даже эти операции запрещены.
Базовые настройки backend: 8N1, без XON/XOFF, RTS/CTS и DSR/DTR flow control.
115200 — начальная настройка линии, не частота АЦП и не измеренная скорость USB.
Открытие порта может менять DTR/RTS согласно драйверу/pyserial; отсутствие
импульса или сброса платы не обещается и подлежит отдельной проверке.

Тайм-ауты ограничивают запрошенное ожидание чтения/записи. Это не жёсткая
гарантия времени возврата ОС, драйвера, `open` или `close`; адаптер не способен
прервать зависший драйвер. Отзывчивость GUI и задержку Stop нужно проверять
отдельно при интеграции. `flush`, очистка буферов и их скрытое ожидание здесь
не вызываются.

## Принятый префикс и неоднозначная запись

Успешный `write(data)` означает только, что backend сообщил известное количество
принятых байтов. Это не ACK команды, не подтверждение доставки в MCU, исполнения
или корректного физического измерения. При коротком результате `n` будущий
владелец контроллера может учесть именно `n` и следующим явным вызовом передать
суффикс `data[n:]`. Возврат 0 не является отключением; расписание следующей
попытки и защита от бесконечного ожидания принадлежат будущему рабочему потоку.

Любое исключение `write`, включая тайм-аут, или результат неправильного типа/
диапазона приводит к `TransportWriteError`, `accepted_bytes=None` и `RECOVERY`.
Часть команды уже могла попасть в устройство. Нельзя подставлять 0, угадывать
префикс по тексту исключения, повторять всю команду или продолжать старый суффикс.
Новая запись, чтение и повторное открытие блокируются `TransportStateError`.

Будущая связь с [контроллером](session-controller.md): известный count передавать
в `written` для того же билета и ровно того суффикса, который был предложен
транспорту; при `TransportWriteError` вызывать `unknown_write(now_ms)`,
не `written(..., 0)`.
Если суффикс больше 4096 байт, рабочий поток должен заранее ограничить очередной
срез и учитывать count относительно него. Этот модуль не вносит таких вызовов
в контроллер. После ошибки нужно сохранить уже полученные фрагменты как
неполные, отменить старые билеты/сеанс, явно закрыть транспорт, явно открыть
выбранный порт, выполнить новую согласованную handshake-процедуру и только
после этого допускать новый захват. Успешный `close/open` сам по себе не доказывает
сброс MCU, очистку всех его буферов или остановку ранее принятой команды.

## Чтение, ошибки и жизненный цикл

`read` может штатно вернуть пустой или короткий `bytes`: это отсутствие данных
к моменту возврата, не EOF и не доказательство потери соединения. Тайм-ауты
ответов протокола отслеживает контроллер. Исключение backend при чтении либо
результат, отличный от точного `bytes` нужной длины, вызывает
`TransportReadError` и `RECOVERY`. Слишком большой результат не обрезается:
иначе были бы молча потеряны байты. Исходное исключение backend сохраняется
как `__cause__`, а наружные сообщения не включают произвольные данные backend.

| Ситуация | Результат |
|---|---|
| Повторный `open` с теми же параметрами в `OPEN` | Ничего не делает; это не проверка физической связи |
| `open` с другими параметрами в `OPEN`, любой `open` в `RECOVERY` | `TransportStateError`; сначала нужен успешный явный `close` |
| Ошибка создания/открытия backend | `TransportOpenError`; если handle получен, одна попытка очистки через `close` |
| Открытие и последующее закрытие при очистке оба не удались | `TransportOpenError.cleanup_error` содержит отдельный `TransportCloseError`; обе исходные причины сохранены; handle остаётся в `RECOVERY` |
| Ошибка `close` или backend всё ещё показывает открытый порт | `TransportCloseError`, handle сохраняется, I/O и новое открытие заблокированы |
| Следующий явный `close` после неудачного закрытия | Повторно закрывает тот же handle; новый backend не создаётся |
| Подтверждённый `close` | `CLOSED`, имя и ссылка на backend очищены; повторный `close` безопасен |
| Явный `open` после успешного `close` | Новый закрытый backend, только явно переданное имя порта |

Все ошибки наследуются от `TransportError`; типы открытия, чтения, записи,
закрытия, аргументов и состояния различны. `KeyboardInterrupt`/`SystemExit`
не скрываются: прерванная backend-операция оставляет транспорт в `RECOVERY`,
чтобы владелец мог закрыть его в своём `finally`. Финализатора с неявным I/O нет.
Владелец обязан обработать неудачу закрытия и не объявлять ресурс освобождённым
до успешного `close`. Ошибка чтения сама по себе не доказывает именно физический
обрыв: причиной также может быть backend/драйвер.

## Инъекция backend и проверка

Фабрика `backend_factory(**kwargs)` — доверенная граница тестирования, а не
песочница для произвольного кода. Каждый вызов должен вернуть новый закрытый
pyserial-совместимый объект: `port`, строго булев `is_open`, методы `open`,
`read(size)`, `write(bytes)` и повторно допустимый `close`. Конструктор получает
`port=None` и все настройки, перечисленные выше. Адаптер проверяет подтверждение
открытия/закрытия и результаты I/O. Он не может ограничить память или время,
которые нарушающий контракт backend тратит до возврата.

Из каталога `host/`, без pyserial, GUI и физического порта:

```sh
python -m unittest discover -s tests -p test_transport.py -v
python -O -m unittest discover -s tests -p test_transport.py -v
```

Fake-тесты проверяют точные аргументы конструктора, отсутствие раннего импорта/
открытия, пустое/частичное чтение и запись, границу 4096, некорректные результаты,
тайм-аут после частичной приёмки, отключение как исключение, ошибки открытия/
очистки/закрытия, явный повторный жизненный цикл и неизменность аргументов/
состояния при отклонении. Ни один тест не открывает реальный порт; тест штатного
ленивого пути подменяет `serial.Serial` fake-фабрикой.

## Проверенные первичные источники и оставшаяся работа

Проверено чтением официальных документов и исходников 10.10.2026:

1. [pyserial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html):
   конструктор с указанным портом открывает его сразу, с `None` оставляет закрытым;
   чтение с тайм-аутом может быть коротким; `write` возвращает количество,
   тайм-аут записи вызывает исключение. `close` закрывает немедленно;
   открытие может воздействовать на DTR/RTS. Эти сведения определяют границу
   адаптера, но не подтверждают работу конкретного драйвера.
2. [Официальный Windows backend](https://github.com/pyserial/pyserial/blob/master/serial/serialwin32.py),
   `Serial.write`: при `write_timeout=0` ветка `ERROR_IO_PENDING` возвращает
   полную длину без достоверного окончательного count ОС. Поэтому нулевой
   тайм-аут записи здесь запрещён. При положительном тайм-ауте неполная запись
   может вызвать `SerialTimeoutException`; префикс через это исключение
   достоверно не передаётся.
3. [Официальный POSIX backend](https://github.com/pyserial/pyserial/blob/master/serial/serialposix.py),
   `Serial.write`: тайм-аут может возникнуть после `os.write`; автоматическое
   повторение исходного буфера поэтому небезопасно. Обработка неизвестного
   count одинаково консервативна для обеих платформ.

Ссылки `master` описывают просмотренные исходники, не закреплённую зависимость
проекта. Для сравнения доступны опубликованные исходники
[Windows v3.5](https://github.com/pyserial/pyserial/blob/v3.5/serial/serialwin32.py)
и [POSIX v3.5](https://github.com/pyserial/pyserial/blob/v3.5/serial/serialposix.py).

Выбор/закрепление версии pyserial, установка, lock/hashes, лицензия и включение
в Windows-пакет остаются открытой задачей. Зависимости в этой итерации не меняются.
GUI, рабочий поток, контроллер, эмулятор, общая CI и shared wire-контракт
не изменяются. Проверки на Windows 10, реальном COM/native USB, отключении кабеля,
плате, низком напряжении и зажигании не проводились. Fake-тесты подтверждают
только контракт адаптера; они не являются аппаратной или Windows-приёмкой.
