# Панель ограниченного потокового просмотра

Дополнение 19.10.2026: [producer/domain декларация](stream-provenance.md)
показывается из сохранённой identity для live, записи и no-R попытки.
Только явно объявленный `completed-dma-v1` получает DMA-domain подписи;
старые записи сохраняют прежнюю интерпретацию. Номинальная шкала времени и
ограничения физической полноты видимы после reopen.

Локальный исходный компонент для [issue 191](https://github.com/font-weight/stm32_motortester/issues/191).
Это не второй исполняемый интерфейс и не новая Windows-сборка. `gui.py`,
acquisition/runtime, COM, wire-контракт, упаковка и проверенная сравнительная
сборка не изменяются. Панель не содержит START/Record/Stop и не соединяет
независимые старые окна в непрерывную запись.

## Встраивание и входы

`StreamViewerPanel(parent, event_config=None, event_capacity=4096)` — QWidget
в той же тёмной русской стилистике, с PySide6/pyqtgraph из существующих зависимостей.
Нет main/нового приложения. Родитель должен вызвать `shutdown()` при завершении;
`closeEvent` и уничтожение QObject тоже безопасно закрывают mailbox.

Все методы, кроме `post_live_snapshot`, вызываются в GUI-потоке:

- `open_path(path)` проверяет `.mtstream` в worker, не в GUI. Новый выбор сразу
  очищает прежний источник; ошибочное открытие оставляет пустую панель с ошибкой.
  Поддерживаются v1 и v2; их строгие storage readers остаются раздельными.
- `load_recording(recording)` принимает immutable `StreamRecording`, уже
  полученный из `recover` либо `recover_attempt(...).recording`, если он существует.
  Сам recover вызывающая сторона выполняет вне GUI. `AttemptReport` без recording
  не является waveform reader; его статус можно открыть через `open_path`.
- `begin_live(StreamIdentity, event_config=None, event_config_revision=0) -> LiveHandle`
  явно меняет источник/поколение панели. Настройки событий задаются keyword-only;
  изменение настроек требует нового вызова begin_live и нового детектора.
  Смена identity никогда не происходит по приходящему пакету.
- `post_live_snapshot(handle, LiveSnapshot) -> bool` разрешён из producer
  thread. Latest-only mailbox заменяет непрочитанный snapshot. Старый handle,
  другая identity, повторный/убывающий sequence и закрытая панель отвергаются.
- `select_range(start, stop)`, `show_whole_recording()`, `follow()`,
  `previous_event()`, `next_event()` управляют просмотром. Все диапазоны
  `[start, stop)` — точные целые raw-индексы.
- `view_requested(Selection)` сообщает намерение пользователя для внешнего
  live-display producer; сигнал не передаёт транспортные блоки.

LiveSnapshot содержит immutable identity, монотонный sequence, границы
проверенного источника, предварительно рассчитанный Envelope, явно сообщённые
loss_samples/состояние хвоста/до 16 флагов. В envelope ≤2048 исходных точек,
≤65536 отсчётов диапазона, до одного verified-prefix segment и трёх явных границ (prefix/fault/suffix).
Это вход для будущего адаптера, а не реализованный device stream или запись.
Создавать/прореживать snapshot следует вне GUI. Панель повторно проверяет
согласованность и преобразует координаты вне GUI.

В follow отображается свежий envelope хвоста той же выбранной ширины. При
ручном zoom/pan следование отключается; snapshot другого диапазона не меняет
выбор или график. Producer должен ответить envelope точно запрошенного диапазона;
панель не выдумывает отсчёты из старой огибающей. Вертикальный масштаб сохраняется.
Запрос live никогда не превышает 65536 отсчётов. Попытка более широкого zoom
ограничивается этим бюджетом с явной подписью; видимый X-диапазон сразу возвращается
к допустимой ширине. Producer получает только исполнимый диапазон. Для широкого
сохранённого файла отдельно остаётся обзорный индекс, его диапазон не сужается.
Настроек захвата/новых spinbox/combobox нет. Колесо на plot остаётся zoom;
при будущих настройках обязателен существующий wheel-protection pattern.

### Неизменяемые recent-live события

Дополнение на базе принятой offline композиции `b5a05b83`: изменены только
`stream_view.py`, `gui_stream.py`, два прямых теста и две инструкции. Entry point,
COM, запись, session, bridge/controller, firmware и прежняя сравнительная поставка
не меняются. Сам live producer/кольцо/receiver эта панель не реализует.

`begin_live(identity, event_config=config, event_config_revision=revision)`
закрепляет immutable настройки и revision за возвращённым handle. Producer
подаёт каждый проверенный блок в `EventDetector(..., retention="recent")`
независимо от частоты redraw; GUI не сканирует raw повторно ради поиска событий.
Для публикации используется:

- `LiveEventIndex(handle, sequence, config_revision, config, events, status, capacity)`;
  events — `detector.retained_events`, status — `detector.status`, capacity ≤4096;
- `LiveSnapshot(..., raw_available_start=ring_start, event_index=index)`;
  `first_sample_index/end_sample_index` остаются абсолютными границами источника,
  а `[raw_available_start, end_sample_index)` — реально доступным raw кольцом
  шириной ≤65536. Старые envelope-only callers могут не задавать новые поля.

Event payload optional только для источника без настроек live событий. Если
настройки закреплены, отсутствие payload, другой config/revision/handle либо
sequence отвергаются. Исходные event bounds могут предшествовать текущему
`raw_available_start`: это допустимые старые метаданные, а не ошибка архива.
Closed entries/pending/status/config должны быть immutable и согласованными:
глобальные ordinal строго последовательны, trigger отсортирован, исходные
bounds лежат в обработанном префиксе источника, pending выделен отдельно.
`processed_until` running-детектора равен end источника; после явного fault
допустим меньший обработанный префикс. Видны настройки, eviction, pending,
исходные flags, suppressed crossings и первая граница отказа.

Будущий controller обязан отделить receiver owner от display worker. В receiver
подаётся каждый валидированный raw block в единственный детектор; под коротким
lock передаётся только ограниченный raw/event snapshot либо его immutable
состояние. Построение envelope, создание LiveEventIndex/LiveSnapshot и их
вложенная bounded-валидация должны выполняться **в display worker, вне receiver
owner и его критических секций**. Вызов post_live_snapshot также делает полную
валидацию до собственного lock, поэтому вызывать его из RX-path нельзя.
Совместный scheduler/backlog тест остаётся отдельным обязательным стыком;
одна эта панель не подтверждает бюджет небольшой device-очереди.

Создание и вложенная bounded-валидация tuple выполняются вне mailbox lock;
под lock повторно проверяются текущие handle/identity/config/sequence и
монотонность source end, ring start, completed/evicted count и processed_until.
Первый terminal outcome/discontinuity не может исчезнуть в новом snapshot.
Mailbox по-прежнему latest-only: нет per-block/per-event Qt сигналов или
растущей истории. Панель удерживает только ограниченные snapshots и один
старый выбранный EventEntry для честного сообщения о вытеснении.

Previous/Next работают с глобальными ordinal. Если **весь исходный**
`[start_index,end_index)` доступен, `view_requested` получает именно его.
Если отсутствует хотя бы один отсчёт предыстории/хвоста, запрос не посылается,
старые pixels очищаются, исходный выбор и bounds сохраняются с явным
`unavailable`/«недоступен в live-памяти». Clamp на более новые samples не
выполняется. При вытеснении выбранного ordinal сохраняется отдельное сообщение,
другое событие автоматически не подставляется. Явные Previous/Next, ручной
выбор или «К хвосту» позволяют сделать новый выбор; источник/close сбрасывают
выбор. Новые snapshots другого viewport не заменяют удерживаемый диапазон.

Вытеснение raw из live-памяти и метаданных из индекса не является потерей
raw архива и не прибавляется к source loss. Envelope `complete` означает лишь
покрытие отображаемого диапазона. Ни он, ни завершение порогового контекста,
ни номинальные 50 kS/s не доказывают полного физического разряда или fsync.
После Stop/finalization можно заново открыть сохранённый файл строгим reader
и использовать raw zoom/overview всей записи. Растущий journal не читается;
автоматический offline индекс всё ещё имеет явный предел 4096 событий.

### Размер панели и доступность текста

Один scroll-контейнер сохраняет читаемый размер toolbar, plot и статусных подписей.
При меньшем внешнем размере появляются обычные полосы прокрутки; содержимое
может быть шире/выше viewport. Подписи получают полную высоту по своей ширине
и не перекрывают временную ось. Проверены внешние 1000×710, 800×600 и 600×400
с фактическим stylesheet 13 px и 22 px. Это ограниченный Qt/offscreen контракт,
не универсальная гарантия DPI, Windows или любого шрифта. События колеса на plot
по-прежнему масштабируют график; для перемещения всего содержимого доступны
scrollbar и прокрутка вне plot. Встраивающий код не должен скрывать scrollbar
или навязывать фиксированную высоту внутренним подписям.

## Ограниченный исполнитель и отмена

У панели один работающий daemon Python job, один заменяемый ожидающий request,
один completion mailbox и один latest live mailbox. GUI QTimer опрашивает их
раз в 20 ms. Нет сигнала на блок, растущей очереди или item на каждый пакет.
Новый запрос не создаёт второй job до завершения первого.

Каждый результат связан с локальным source revision, request revision, а для
файлов ещё с конкретным immutable StreamRecording (recording/file identity).
Повторное открытие файла с той же stream identity всё равно меняет source token.
Поздние scan/render/live/open ответы не возвращают прежний источник и не меняют
новый выбор. Snapshot sequence дополнительно защищает live display.

Read/minmax, index, summary и перевод raw-index → локальные float координаты
выполняются в worker. Только установка готовых bounded массивов и рисование Qt
остаются на GUI. Close немедленно инвалидирует токены, отменяет очередной job и
между scan chunks, закрывает sink; worker не хранит QWidget и не испускает Qt
сигналы. Удаление QObject без close также закрывает sink.

Нельзя принудительно прервать заблокированный системный read/recover. Закрытие
не ждёт его; daemon может закончить свою ограниченную операцию позже. Пока он
работает, новый источник ожидает единственный worker. Это ограничение ОС и
данного исполнителя, не проверенная гарантия задержки Windows. Recover имеет
storage hard cap файла, но не разбит на отменяемые шаги данным API.

## Детальный диапазон и обзор всей записи

До 65536 samples используется настоящий Viewport и `minmax_envelope`;
его бюджет не растягивается для многочасовой шкалы. Повторные pan/zoom читают
только выбранный bounded диапазон. Сначала вычитается целый start из raw index,
затем разность переводится во float и делится на номинальную Fs. Это сохраняет
соседние позиции при абсолютных индексах >2^53. Локальный ноль и точный выбранный
raw-диапазон указаны текстом; Fs не называется калиброванной.

Для всей записи реализован отдельно согласованный небольшой обзорный индекс:
фиксированные ≤4096 bins по диапазону проверенного префикса. В каждом хранятся
исходные first/min/max/last с их точными индексами, без усреднения. Совпадающие
точки не дублируются, порядок сохраняется. ≤16384 points на весь обзор.

Один scan job обрабатывает ≤65536 samples, чтение идёт chunks≤8192. Между ними
проверяется отмена. Обзор и пороговый индекс строятся за один фоновый проход.
Производный индекс ограничен ≤4096 events и одним pending. Достижение ёмкости
event index не прерывает raw storage и не мешает достроить overview. Эти лимиты
продукта не задают длину физической записи.

После каждого шага возвращается bounded immutable snapshot с `covered_until`.
До конца явно отображается «строится; неполный». Ошибка оставляет только
обработанный префикс и подпись «неполны»; close сообщает отмену. Результат может
содержать последний ещё неполный bin, поэтому при следующем шаге его points
заменяются. Raw не удерживается дольше текущего chunk.

Широкий выбранный диапазон рисуется из этого отдельного summary и явно подписан
«ОБЗОР». На границах частичных bins нет гарантии полного min/max внутри нового
поддиапазона: точные detail доступны при ширине≤65536. Whole-recording view имеет
реальные крайние samples и глобальные экстремумы каждого bin. Это ограниченная
одноуровневая основа; persistent/multiresolution cache здесь отсутствует,
повторное открытие заново строит обзор. Длительность файла ограничена storage,
произвольные многочасовые записи этим этапом не заявляются.

## События и честные подписи

Пороговые настройки передаются явно как EventConfig; аппаратные значения не
выдумываются. Если настроек нет, строится только обзор. Настройки и лимит
контекста видны в подписи индекса. Prev/Next работают по bounded immutable
metadata, без чтения raw в GUI и без списка на каждый транспортный блок.

Выбор события показывает весь сохранённый `[start_index, end_index)` вместе с
trigger/baseline/settled и flags. `right_truncated`, `left_truncated`,
`tail_ambiguous`, `context_limit`, `event_capacity`, clipping и разрыв не
скрываются. Диапазон >65536 показывается как обзор и допускает дальнейший zoom,
а не незаконное расширение detail. Физические горение/затухание, номер цилиндра
и исправность не определяются; даже событие без флагов не доказывает полного
физического разряда. Его хвост требует согласованного измерительного контекста.

Обнаруженная ошибка чтения/целостности текущего файла сохраняется отдельно от
состояния отрисовки. Кеш можно рассматривать, но и status, и storage предупреждают,
что источник отклонён, а pixels относятся к ранее проверенным байтам. Успешная
отрисовка или переход к cached overview не стирают первый отказ. Только явный
новый источник/повторное открытие сбрасывает latch; ошибочное открытие не возвращает
старые кеши. GUI не делает файловых проверок для этого предупреждения.

Storage status отдельно показывает terminal, recovery_issue, неизвестный хвост,
заявленные loss_samples, discarded bytes и первый failure. Envelope complete
означает только покрытие выбранного диапазона и не стирает неизвестный terminal.
Синтетический источник отмечен постоянно; device origin — заявление metadata,
не доказательство реального прибора. Live display не подтверждает запись на диск.

### Раздельные состояния v2

Версия выбирается чтением только фиксированных 8 magic bytes через существующий
storage `_open_attempt_read`, с `_unchanged` до/после чтения и после строгого
recovery. Guarded descriptor остаётся открыт на время второго открытия reader,
так что подмена между ними тоже отвергается. Для v1 вызывается только `recover`,
для v2 — только `recover_attempt`; неизвестный magic или ошибка выбранного reader
не запускают fallback. Новый парсер JSON/кадров/raw не введён. Приватные path/size/
mutation guards заимствованы у точного storage pin, поэтому их изменение требует
повторной проверки этой композиции. Одновременно открыты не более двух read handles.

- Один проверенный preparation header показывает только сохранённую подготовку
  и неизвестный исход. R не установлена в файле; это не доказательство, что END
  опередил DATA, что выбора не было в оперативной памяти или что старый fsync вернулся.
- `ended_unbound`, `cancelled_unbound`, `failed_unbound` показываются как разные
  сохранённые исходы. R и `[R,E)` не выдумываются. Сохраняются первый failure,
  observed, Stop/request id, generated/transmitted end и известный/неизвестный loss.
- Полный S или первый B без подтверждённого C/T может сохранить свидетельство R,
  но не даёт восстановленный `StreamRecording`. Панель сообщает этот R отдельно,
  не рисует пустой интервал и не строит обзор/события.
- S с действительным T допускает установленный пустой direct-START `[R,R)`:
  он остаётся записью с настоящим R и terminal, хотя график пуст и навигация выключена.
- Выбранный v2 `recording` использует прежние bounded lazy read/detail/scan/overview
  и sticky source-failure latch. При оборванном хвосте доступны только подтверждённые
  raw samples; восстановленные байты не становятся подтверждением полноты хвоста.

Loss сохраняется именно как заявленный счётчик источника. Даже 0 может сочетаться
с более коротким файлом и первым host/capacity failure; он не заменяется вычисленной
суммой потерь. Читаемый T/U и `clean_stop_reported` не подтверждают успешный возврат
старого finish/fsync. Это ограничение явно видно в статусе, включая пустые попытки.

## Проверка

Тесты в `test_gui_stream.py` используют настоящие Qt widgets и синтетические
saved записи. Основные сценарии: ограничение summary/read budgets; общий scan,
last point/DC, >2^53; event context/capacity; unknown terminal vs complete plot;
заблокированный reader, source swap с одинаковой identity, rapid latest-only
navigation, close/delete while worker; live sequence/generation; реальные wheel
и drag, стабильный Y; пустой/неверный файл и неверный immutable snapshot.

Для совместимости v2 заранее заданы: прежние v1 regressions; preview selected с
R выше 2^53; установленный direct empty; no-R END/cancel/failure/prepared; torn
header/S/B/T и неподтверждённый selection; malformed header, symlink и mutation
между dispatch/recovery; sticky v2 read failure; поздний status-only open после
смены источника/close; реальные нормализованные session → PreparedStreamWriter →
reopen → panel стыки. Отдельно проверяются source loss 7/0/None при source-first
и local-first более коротком архиве, а также читаемые header/T после fsync exception.
Тестовый владелец `_RealStorageProbe` переиспользуется из `test_stream_session`;
production adapter/transport этим не добавляется.

Воспроизводимый из корня worktree запуск без установки зависимостей:

```sh
# Активируйте свою среду с существующими зависимостями host.
export PYTHONPATH="$PWD/host"
export QT_QPA_PLATFORM=offscreen
python -m unittest discover -s host/tests -p test_gui_stream.py -v
python -O -m unittest discover -s host/tests -p test_gui_stream.py -v
```

Фактические логи и hash исходников сохраняются отдельно с отчётом проверки.
Qt/offscreen Linux не заменяет нативную Windows/packaging, sustained device stream,
wire/Stop/backpressure интеграцию, низковольтный опыт или проверку зажигания.

Первый кандидат `ecfbc4af` прошёл 16 авторских тестов каждого режима, но
независимое R1 выявило два функциональных дефекта: невозможный live zoom-request
и исчезновение известной ошибки источника после cached overview; также найдено
перекрытие подписей на минимуме/22 px и непереносимая команда проверки.
Исходный кандидат, его отрицательные логи и pixels сохранены отдельно.
Исправленный кандидат содержит постоянные regression tests этих сценариев;
его точные результаты и независимый вердикт привязываются к новому commit.
Тогда приёмка панели и планируемой десятифайловой композиции оставались отдельными
воротами. Текущая тринадцатифайловая композиция и v2-совместимость описаны выше.
