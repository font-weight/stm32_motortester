# Ограниченный сборщик LV-001

Черновой headless-путь сохранения одного опыта: отдельное полное прогревочное
окно и затем ровно 20 запланированных попыток. Проверяется программой на
синтетическом byte-peer. Это не выполненный LV-001, не приёмка Windows/USB/АЦП
и не разрешение физического подключения. Плата, паспорт безопасного подключения,
реальные VDDA/ADC_IN и независимая проверка времени остаются отдельными условиями.

Основание методики: [validation.md на A db09c263](https://github.com/font-weight/stm32_motortester/blob/db09c263c022c27723fd9de9e4a79905097767c6/docs/validation.md).
[Wire-кандидат того же SHA](https://github.com/font-weight/stm32_motortester/blob/db09c263c022c27723fd9de9e4a79905097767c6/protocol/wire-v0.1.md)
остаётся предложением, не новым принятым общим контрактом. Недостающие сведения
старого формата перечислены в [PR108](https://github.com/font-weight/stm32_motortester/pull/108#issuecomment-6118660346)
и [независимом отчёте A](https://github.com/font-weight/stm32_motortester/pull/106#issuecomment-6118914570).

## Что именно сохраняется

`motortester.lv_collector` использует существующий `AcquisitionRuntime` и
не меняет `Capture`, строгий `.mtcap` v1, firmware или протокол. Каждый полный
массив сохраняется обычным `.mtcap`; обязательные исходные сведения опыта
сохраняются рядом в отдельном version1 JSON. Неполные фрагменты остаются
фрагментами JSON с offset и missing_ranges; недостающие коды не дополняются
нулями. Отказ до BEGIN имеет статус/транскрипт без выдуманного Capture.

Каждый sidecar сохраняет оригинальные **принятые runtime** HELLO_ACK, CAPS,
CONFIG_ACK, BEGIN, END, ABORT и STOP_ACK, если соответствующий кадр был принят.
У кадра есть session, sequence, request_id, исходный payload_hex и все
расшифрованные поля. В том числе сохраняются:

- generation, config_id, window_id, profile и число отсчётов;
- числовые trigger_kind/index, source, channel, edge, external_edge_id,
  level_code, pretrigger_samples и исходная quality_flags;
- исходный WINDOW_END.samples_crc32; он отличается от SHA256 файлов;
- timer_clock_hz, timer_psc/arr, adc_clock_hz, adc_sample_cycles_x2;
- объявленный firmware_build, capability/mode/source/edge bits, принятый Auto
  timeout и запрос Fs 50000 Гц.

Настройки ограничены Auto, аналоговым source0, profile1, pretrigger0. Edge,
level_code и timeout100…60000 мс проверяет существующий Config, затем CAPS и
CONFIG_ACK. Раннее настоящее пересечение сохраняет реальные поля запуска.
Timeout не подставляется ради ожидаемого результата опыта.

`RunIdentity` требует явный origin (`simulator`/`device`), application_commit
и application_tree (точные 40-значные Git SHA либо явный `TBD`). Остальные поля:
application_build, firmware_commit, firmware_build_identity, board_json_sha256,
hardware_passport_id, schematic_id, vdda_measurement, adc_in_measurement,
meter_and_uncertainty, independent_timebase, measured_fs_and_uncertainty.
Неизвестные значения имеют строку `TBD`. В текстах измерений caller указывает
значение/единицы, точки и время измерения, прибор/диапазон и основание
неопределённости. Номинальные 3,3 В не считаются измерением; объявленный build0
не подменяет SHA прошивки. Поля являются сведениями caller, не автоматической
проверкой подлинности платы или сборки.

В `implementation` отдельно закреплены:

- локальная база `33696f8a41d70196d7870a92b24d01def44a1eb2`;
- опубликованная база PR108 `1af7c7c27e7eaa6559138b055ed40c7e3114abb1`;
- их одинаковое дерево `2ed75f6d5d9993af47a79cbfa0eb1e6b3568b2e9`;
- proposal SHA `db09c263c022c27723fd9de9e4a79905097767c6`;
- исторические pins модулей session, window и codec.

Локальный и опубликованный commits имеют разные идентификаторы; совпадение
дерева не делает их одним commit. Текущую сборку приложения caller передаёт
отдельно, а историческая строка protocol_version внутри MTCAP не заменяет её.

## Небольшой API

Из `host/` библиотека импортируется без Qt/pyserial и сторонних зависимостей:

```python
from motortester.lv_collector import LVCollector, RunIdentity, State, verify_run
from motortester.session import Config

collector = LVCollector(
    "новая-папка-опыта", transport,
    clock_ms=monotonic_integer_ms, nonce=fresh_nonzero_uint64,
    identity=RunIdentity(
        origin="simulator", application_commit="TBD", application_tree="TBD"),
    config=Config(mode=0, source=0, profile=1, pretrigger_samples=0,
                  edge=0, level_code=2048, auto_timeout_ms=100),
)
collector.start()
# Пока NEGOTIATING: caller вызывает collector.pump().
# READY: caller явно вызывает collector.arm_next().
# ACTIVE/STOPPING: caller регулярно вызывает collector.pump().
# SAVEABLE: caller вызывает collector.persist_attempt().
# После успешного сохранения READY означает возможность следующего явного ARM.
```

Это описание API, не готовый скрипт подключения: transport и часы caller
передаёт явно. Collector не сканирует/не открывает COM, не закрывает транспорт,
не делает reset/reconnect, не запускает поток, не спит и не повторяет команды.
Один владелец вызывает методы последовательно; переданный транспорт нельзя
параллельно использовать извне. Доступ к `runtime.pending_capture` позволяет
прочитать удерживаемый объект, но прямые управляющие вызовы runtime и изменение
внутренних словарей обходят политику collector и не являются допустимым API.

`start()` требует новую папку и записывает индекс всех 21 намерений до HELLO.
После согласования конфигурации состояние READY само ничего не вооружает.
`arm_next()` сначала сохраняет intent конкретной попытки и только потом ставит
ARM в очередь. Сохранённое `arm_queued=null` означает неопределённость после
точки записи intent при crash. Позднее отдельно фиксируются факт постановки
в очередь, число transport-known принятых ARM-байтов, unknown-write и ARM_ACK.
Принятый префикс не означает исполнение команды, TX intent не доказывает даже
принятие префикса, ARM_ACK не доказывает получение полного окна.

Обычный успешный порядок:

1. Runtime создаёт проверенный pending_capture; collector сразу ставит Stop.
2. `pump()` продолжает только нужный обмен. Требуется именно STOPPED event с
   совпавшим request_id и последующий READY без барьеров. Посторонний READY
   не считается подтверждением Stop. RELEASE не выдаётся.
3. `persist_attempt()` пишет исходный Capture, перечитывает и сравнивает все
   поля/коды, пишет sidecar и сравнивает его исходные байты/структуру, связывает
   файлы SHA256 в индексе и проверяет весь индекс с файлами по одному.
4. Только затем `acknowledge()` получает **тот же** исходный объект в READY;
   это локальное освобождение, без RELEASE/rearm. Следующий ARM всегда явный.

Чтение/запись диска до подтверждённого Stop в активной попытке не выполняется.
Таким образом disk latency не удерживает WAIT_RELEASE. Это не гарантия срока
5000 мс: задержка caller/ОС/транспорта и момент принятия END устройством остаются
существенными. STATUS ERROR, неизвестная запись, expiry/timeout, потеря связи
или отказ Stop прекращают серию. Доступный Capture, исходный END и/или
неполные фрагменты сохраняются при `persist_attempt()`. Следующего автоматического
ARM, сброса или скрытой замены неудачного окна нет.

`cancel()` инициирует безопасное завершение; caller продолжает pumping Stop,
затем сохраняет результат. Не начатые попытки становятся cancelled. Прогрев
отдельный, его неудача не заменяется и не превращается в одну из 20 попыток.
После failed/cancelled run новый опыт требует отдельного явного решения caller,
новой папки и нужного реального восстановления транспорта.

## Журнал наблюдения и пределы

Transport wrapper сохраняет RX **до** того, как runtime может отбросить
неправильный кадр или свернуть числовой STATUS ERROR в DEVICE_ERROR. TX intent
фиксируется перед вызовом write; исход после вызова имеет accepted_prefix либо
unknown_write. Число принятых байтов относится только к известному префиксу.
Журнал не объявляет наблюдавшиеся байты firmware-admitted. Неполный кадр,
отклонённая CRC и числовой STATUS остаются исходными hex-байтами, даже если для
них нет accepted frame. Строки исключений backend не сохраняются.

Повтор непосредственно предыдущего целого Frame с теми же type, session,
sequence, request_id и payload отмечается identical_frame_replays. Даже если
runtime корректно игнорировал такой повтор, попытка LV становится failed:
это более строгое правило опыта «дубликатов 0», не утверждение о повреждении
полученного массива или отклонении прошивкой. Полный Capture сохраняется.
Повтор идентичного DATA payload для тех же session/generation/window/offset
отдельно отмечается repeated_data_blocks, в том числе при другом sequence;
он тоже нарушает более строгое правило опыта. Одинаковые значения отсчётов
на разных offset/в разных окнах остаются допустимыми. Для наблюдения
используются ещё один ограниченный decoder, последний Frame и не более 2048
первых DATA payload; их суммарные байты ограничены общим raw-бюджетом журнала.

Фиксированные пределы:

| Объект | Предел |
|---|---:|
| План | 1 прогрев +20 попыток, без расширения |
| Полное окно | 2048 кодов, 4096 исходных байтов |
| Один read/write | 4096 байт |
| Журнал текущей попытки | 131072 байта raw-эквивалента, 8192 records |
| Счётчик последовательных пустых read | 4294967295, coalescing |
| Один sidecar | 2097152 байта |
| Индекс | 65536 байт |
| MTCAP v1 | 147504 байта, существующий MAX_FILE |
| Поле паспорта/identity | 512 символов |
| Основные файлы run | не более 43: индекс +21 sidecar +21 MTCAP |

Общая верхняя граница этих 43 файлов — 47203312 байт; временный файл
atomic_write и сохранённые внешние свидетельства считаются отдельно.

Это пределы данных, а не обещание точного RSS интерпретатора. Hex занимает
вдвое больше raw; Python-объекты, decoder/runtime и временные ограниченные
JSON/файловые копии также требуют памяти. В памяти не накапливается серия
20 окон. Проверка файлов перебирает по одному, итог содержит индекс, не массив
Capture. JSON читается с пределом до parse, serializer ограничивает накопление
во время записи. Входные типы/длины проверяются до копирования. В read заранее
резервируется полная запрошенная порция: это намеренно консервативный предел.

Переполнение останавливает I/O до очередного backend-вызова и отмечается
JOURNAL_OVERFLOW. Уже сохранённая часть журнала остаётся, но полный transcript
не обещается. Huge/wrong-typed backend return не копируется, отмечается
INVALID_READ; для такого нарушившего контракт backend полного RX-журнала нет.
Последовательные пустые polls хранятся счётчиком при первой временной отметке,
не бесконечным списком. Фоновая запись журнала во время acquisition отсутствует.

## Формат и отказ хранения

`index.json` и `attempt-00.json`…`attempt-20.json` имеют канонический UTF-8 JSON:
`format` (`mtlv-index`/`mtlv-sidecar`), `version=1`, `body`, `sha256` канонического
body. Неизвестные поля/версии, повторные ключи, некорректные типы и размеры
отклоняются. Индекс хранит SHA256 целого sidecar и MTCAP; sidecar также хранит
SHA256 MTCAP. SHA защищает от случайного повреждения, не от злонамеренной
перезаписи данных вместе с пересчитанными хешами.

Файлы попыток создаются без overwrite. Перед изменением индекса проверяется
его прежний хеш; atomic_write использует временный файл, flush/fsync и атомарную
замену/создание. Это не транзакция сразу трёх файлов и не универсальная гарантия
при отключении питания.

На диске **никогда не записывается авторитетное `complete`**. После подготовки
21 подходящего файла индекс имеет `sealed_unverified`: он связывает артефакты,
но не доказывает, что прежний процесс дочитал их и выполнил consumer ACK.
`verify_run()` заново проверяет все файлы и возвращает прежние поля индекса плюс
`artifact_integrity=RECOVERED_VERIFIED` и `prior_writer_outcome=UNKNOWN` для
полной сохранённой серии. Для остальных согласованных индексов целостность
имеет `PARTIAL_VERIFIED`. Поля проверки не дописываются в исходный индекс.
Сохранённый state при открытии не превращается в complete. Failed/cancelled
не становятся успешными из-за наличия полного Capture.

Только работающий collector после полного readback и ACK того же объекта
получает **в памяти** `State.COMPLETE`. Остановка процесса сразу после sealing
или повторный отказ диска на readback/rollback оставляют на носителе максимум
sealed_unverified. Повторное чтение может подтвердить 21/21 артефактов, но не
приписывает прошлому процессу успешное завершение/ACK. Это уточнение модели
фиксации устраняет ложное завершение на границе последнего дискового I/O.

При исключении collector пробует восстановить свой проверенный incomplete
индекс, не перезаписывая чужой stale файл. Если повторный отказ диска не
позволяет подтвердить восстановление, storage_status=UNKNOWN; даже оставшийся
sealed_unverified не объявляется успешным исходом прежнего writer. Невозможно
обещать запись сообщения об отказе на уже неработающий носитель.

Права/свободное место/поведение filesystem проверяются
фактическим вызовом, не обещаются заранее.

При disk/stale-path/readback failure ACK и следующий ARM запрещаются; объект
и журнал сохраняются в текущем процессе. Проверенный восстановленный индекс остаётся incomplete/
pending либо показывает только ранее проверенные попытки; при storage_status=UNKNOWN
его состояние нельзя обещать до независимого чтения. Уже созданные файлы
не удаляются и не перезаписываются. Возможные orphan/torn файлы не считаются
закрытой попыткой без подходящей ссылки/хеша из индекса. При crash до сохранения
журнала intent остаётся виден, а полный transcript может быть потерян. Повтор
`persist_attempt()` после ошибки не выполняется автоматически. Не исправляйте
такой индекс вручную ради complete: сохраните папку и исследуйте отказ.

CLI только читает сохранённый опыт:

```text
python -m motortester.lv_collector путь-к-папке
```

Код0: заново проверена целостность 21/21 подходящих артефактов, прогрев отдельно;
это RECOVERED_VERIFIED, исход прежнего writer и его ACK остаются UNKNOWN. Код1:
индекс читается, но хранит лишь частичный/failed/cancelled результат. Код2: файл отсутствует,
повреждён или схема не поддерживается. Это не оценка амплитудной/временной
точности или физического происхождения массива.

## Воспроизводимая программная проверка

Из `host/`, без подключения прибора:

```text
python -m unittest discover -s tests -p test_lv_collector.py -v
python -O -m unittest discover -s tests -p test_lv_collector.py -v
```

Общий GUI-набор отдельно требует уже подготовленные зависимости и offscreen.
Авторские тесты покрывают 21 framed Auto-окно, реальные/timeout поля, разбиение
до одного байта, coalescing, сохранение после Stop, исходный CRC, фрагменты,
ошибочные/дублированные входы, Stop/transport/storage failures, пределы и отмену.
Финальное свидетельство и независимый Critic-B привязываются к точным хешам;
наличие этого списка не заменяет исполненный отчёт и не даёт PASS автору.

Даже полное программное прохождение не подтверждает время установления
источника/тракта, первые физические преобразования, фактическую частоту,
точность ADC, реальный USB или готовность низковольтного стенда. В Auto ранние
отсчёты до timeout могли быть вытеснены из кольца; прогревочное окно не доказывает
их свойства и не разрешает обрезать начало последующих сырых массивов.
