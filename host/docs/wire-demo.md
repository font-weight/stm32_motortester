# HOST-005: синтетический wire → запись → график

**DRAFT.** [Задача и заранее объявленная приёмка](https://github.com/font-weight/stm32_motortester/issues/22).
Это интеграционный пример байтового потока, не USB-драйвер и не реализация
согласования сеанса с прибором. Общий wire-draft ещё не принят.

```sh
PYTHONPATH=host python -m motortester.wire_demo NEW_DIRECTORY
PYTHONPATH=host python -m motortester.wire_demo OTHER_NEW_DIRECTORY --windows 20 --chunk-size 1
```

Нужна только стандартная библиотека Python. Для Windows PowerShell сначала
задайте `$env:PYTHONPATH = "host"`, затем выполните команду без префикса
`PYTHONPATH=host`. Этот пример команды не является выполненной Windows-проверкой.
Папка должна быть новой. Каждый файл публикуется атомарно без перезаписи;
весь набор не является одной транзакцией. При более поздней ошибке уже
проверенные предыдущие файлы сохраняются, а итоговый manifest не создаётся.

## Что действительно проходит через код

1. Детерминированные 2048 кодов превращаются в WINDOW_BEGIN, девять WINDOW_DATA
   и WINDOW_END с CRC исходных 4096 little-endian байт.
2. Настоящие COBS/CRC кадры разбиваются на порции 1…4096 байт и поступают в
   `StreamDecoder`, затем в `WindowReceiver`. Проверяются sequence, session,
   generation/config/profile, длины, диапазоны, END и CRC.
3. Только полный результат без отложенных проверок или противоречивых метаданных
   превращается в неизменяемый Capture. Любая диагностика/неполнота/лишний кадр
   запрещает сохранение успешной записи; хвост без разделителя тоже отвергается.
4. MTCAP сохраняется и читается заново; все коды сравниваются побитно. По вновь
   прочитанным данным создаются CSV и SVG. `manifest.json` хранит SHA-256 записей.

Окна используют Normal/analog/rising/profile1, уровень2048, предысторию512,
номинальные50кГц. Исходная синусоида имеет явный контрольный префикс
`(0, window_id, 256, 4095)`; rail-флаг установлен по этим кодам. Это намеренно
синтетический массив, а не измерение физического сигнала. У двадцати окон
возрастают window_id и последовательность кадров. UUID записи — документированное
нулевое расширение 64-битного синтетического session в128бит, не новый wire-формат.
Происхождение всегда `simulator`; версия прошивки отсутствует; версия протокола
содержит точный непринятый draft SHA. UTC — фактическое время приёма хостом,
поэтому бинарные файлы между запусками могут различаться при одинаковых кодах.

## Ограничения API

`synthetic_window(window_id=1, first_sequence=1)` возвращает tuple кодов и bytes.
Окна1…20; sequence ограничен так, чтобы все11 кадров не достигали зарезервированного UINT32_MAX.
`capture_from_synthetic_stream(data, ...)` принимает только bytes длиной1…16384,
строгие целые параметры без bool/неявного преобразования и один такой пример.
`save_synthetic_stream(path, data, ...)` сначала полностью проверяет поток,
только затем вызывает безопасное сохранение. Это не универсальный импорт сырых
USB-логов: повторные кадры, иной layout блоков или дополнительные события
отвергаются политикой этого узкого примера.

Виртуальное время растёт на1мс каждые64порции. Так проверяется разбиение потока,
но не скорость USB и не реальная точность deadline. Timeout/disconnect/неполные
фрагменты отдельно проверяются HOST-004. HELLO/CAPS/CONFIG/ARM/Stop и выходной
TX-поток здесь отсутствуют; ожидаемый контекст задан явно для синтетики.
Auto+external, Windows10, реальное устройство и аппаратные характеристики
этот пример не принимает. Критик должен отдельно проверить точный итоговый SHA.
