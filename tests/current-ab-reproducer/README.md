# Текущая прошивка → runtime ПК: воспроизводимые нативные проверки

**DRAFT.** Это комплект программных проверок на Linux без подключения прибора.
Он заново собирает два C-моста и запускает опубликованный Python runtime B,
не заменяя его тестовым парсером. Ничего не скачивает, не устанавливает,
не прошивает и не открывает COM/USB. Он не подтверждает GUI, Windows 10,
физическую частоту, АЦП, USB платы или аппаратный сброс.

## Точные входы

Нужны отдельные экспортированные деревья или checkout:

- A: PR106 `db09c263c022c27723fd9de9e4a79905097767c6`, tree
  `c9cddf4d2bbf5b9dd4bb4c996e55eca90eac2b1f`.
- B: PR108 `1af7c7c27e7eaa6559138b055ed40c7e3114abb1`, tree
  `2ed75f6d5d9993af47a79cbfa0eb1e6b3568b2e9`; передать его каталог `host/`.
- Этот пакет — отдельный исходный каталог с `reproduce.py` и `inputs.json`.
  Его commit записывается в PR; не использовать изменённые скрипты под прежним SHA.

Манифест проверяет 168 исходных/нормативных/вспомогательных файлов A,
все 214 файлов `host/` B и семь локальных fixture/probe-файлов по SHA256,
размеру и POSIX mode. Это точная проверка перечисленных входов, не заявление,
что каждый файл компилируется: полный runtime использует 16 project C units
и TinyUSB core/CDC/FIFO; оконный мост — семь C units. Объявленные SHA деревьев
дают происхождение; весь Git commit раннер не пересчитывает.

Дополнительно проверяется непосредственный файловый состав каталогов поиска
C-заголовков и полный состав vendor,
полный файловый состав B и отсутствие лишних файлов пакета, способных
подменить импорт/заголовок. Не добавлять в исходники `__pycache__`, `.so`
или генерируемые результаты. Для A каталоги `host/` не используются. Перед компиляцией ровно 168 закреплённых
файлов A копируются в свежий изолированный `source-a/` внутри output, повторно
проверяются и только оттуда подаются patch helpers и компилятору. Лишний
вложенный заголовок вне этого списка не копируется и не может подменить
системный include. Не все посторонние файлы A отвергаются; они не входят в
компилируемое дерево. Исходный A остаётся read-only, его hash проверяется снова.
Wire-кандидат и codec-вектор закреплены в манифесте; они остаются непринятым
общим контрактом до применимых независимых заключений обеих сторон.

## Запуск

Требования: Linux, Python 3.11+ и установленный GCC 14. Фактически проверенная
среда автора: Python 3.12.14, GCC 14.2.0; точные сведения и hash компилятора
пишет receipt. Весь допустимый диапазон версий Python не проверен. Python-зависимости
этих headless-проб входят в стандартную библиотеку; PySide6/pyserial не нужны.
Выполнение и квалификация на другой среде не предполагаются автоматически.

Перед запуском заменить путь к reproduce.py и три пути аргументов на реальные
абсолютные пути. Они должны
быть нормализованы, не содержать symlink-компонентов или вложенных symlink-файлов/каталогов;
пробелы допустимы при
кавычках. A и B — отдельные деревья. Выходной каталог ещё не существует,
его родитель уже существует, он находится вне A, B и пакета.

```sh
python3 -I -B '/absolute/package/reproduce.py' \
  --a-root '/absolute/A checkout' \
  --host-root '/absolute/B checkout/host' \
  --output '/absolute/results/current-ab-run-1'
```

По умолчанию используется `/usr/bin/gcc`, его допустимый системный symlink
разрешается явно. Другой существующий абсолютный путь можно передать через
`--cc`. Не запускать Python с `-O`: проверки fixture используют assertions.
Повторный прогон требует нового выходного каталога; старые результаты
не перезаписываются. Не удалять неудачный прогон ради успешной истории.

## Что выполняется

1. Проверка всех входов и отсутствия подменяющих файлов до создания результатов.
2. Для каждого режима `strict` и `sanitize`: точные существующие TinyUSB patch
   helpers A, штатная test-only DCD-инструментация, компиляция runtime-моста
   и оконного моста. Все argv, версии, stdout/stderr и exit записываются.
   Модель MMIO/DCD/IRQ явно отделена от target execution.
3. Шесть actual `AcquisitionRuntime.pump()` сценариев:
   - ADC transfer до выделения окна: ERROR1 без фиктивного массива;
   - allocated deadline: ABORT3 до BEGIN, затем ERROR2;
   - реальный `mt_runtime_step`, driver TE и уже ожидающий Stop;
   - ранее переданное потребителю полное окно сохраняется при новом ADC fault;
   - удерживаемое окно сохраняется при настоящем A WAIT expiry ERROR3;
   - фрагмент 250 отсчётов сохраняется при disconnect и передаче владения
     перед явно моделируемым reset/new HELLO.
   Только случай driver TE с pending Stop выполняет полный A runtime.
   Остальные пять используют настоящий controller/link/TX с синхронной
   моделью оборудования.
4. Двадцать различных окон Normal/analog, по 2048 кодов. Реальный A
   controller/link/TX выдаёт байты, B создаёт проверенный Capture. Для каждого
   сравниваются исходные коды, все 17 текущих Capture-полей и 25 MTCAP-ключей,
   запись/повторное открытие и побайтовое повторное кодирование. Один ARM,
   19 RELEASE-продолжений, финальный Stop с удержанным двадцатым окном;
   проверяются отсутствие самопроизвольного RELEASE и повторного запуска.
5. Сравнение 39 boundary и 107 roundtrip артефактов между двумя режимами,
   затем повторная проверка исходников. Пути/хеши бинарников во входных
   манифестах режимов ожидаемо отличаются и не входят в эти 146 артефактов.

`sanitize` включает AddressSanitizer/UndefinedBehaviorSanitizer C-кода.
`detect_leaks=0` указан явно: LeakSanitizer не квалифицирован в исходной
среде под ptrace. Python не инструментирован санитайзером. Каждый внешний
непосредственно запущенный процесс ограничен 180 секундами; при timeout или
ненулевом exit завершается только созданная раннером группа процессов.
Успешный exit не доказывает отсутствие отделившихся от этой группы процессов;
пакет не является sandbox для произвольного недоверенного компилятора. Внутренние обращения к мосту также ограничены.
Потеря временного окружения или принудительное завершение самого раннера
не гарантирует финальный receipt: незавершённый результат нельзя считать PASS.

## Результаты и границы

Сводка — `receipt.json`, argv и отдельные stdout/stderr находятся рядом.
Полные host/device wire, трассы команд, снимки состояния, MTCAP и исходные
uint16-le массивы сохраняются в `strict/` и `sanitize/`. Отсутствие итогового
`status=PASS`, failed command либо input drift означает непрошедший прогон.
Количество сценариев само по себе не является оценкой качества.

MTCAP сохраняет нынешнюю модель Capture, но **не** все исходные wire-поля:
нет отдельных generation/config_id, полного CAPS/CONFIG_ACK, исходного
WINDOW_END CRC, полных timer/ADC-настроек, числового quality mask и журнала
всех STATUS. В этих проверках исходные байты сохранены отдельно. Маркер
`protocol_version` в записи — прежняя константа B, не текущий Git SHA;
firmware build `0` тоже не заменяет идентичность сборки. Физические измерения,
паспорт платы, прогрев и реальная серия LV-001 здесь отсутствуют. Нельзя
объявлять эти файлы полной проверкой LV-001 или новым форматом приложения.

В двадцатиоконной пробе время детерминированно моделируется; сохранение перед
ACK не доказывает укладывание реальной дисковой операции в 5000 ms. Будущий
операторский collector отдельно должен соблюдать deadline/Stop и сохранять
все попытки/ошибки. Успешный headless runtime не доказывает Qt-доставку,
сохранение пользователем или физическое действие GUI-флажка reset.

Происхождение fixture и сохранённые ограничения — [PROVENANCE.md](PROVENANCE.md).
Совместная приёмка протокола, Critic-B, Windows и аппаратура остаются отдельными.
