# TX002 / Issue70: независимая проверка ARM и STOP-стека

Статус: **PASS_SUPPORTING_ARM_COMPARISON_ONLY**. Окончательный прогон: `evidence-r3/receipt.json`. Каталоги `evidence-r1` и `evidence-r2` — промежуточная отладка самого проверяющего runner; для приёмки использовать r3 и сохранённый в нём `runner-snapshot/`.

## Вывод

Под теми же фактическими флагами исходной 25-unit closure собственный кадр `mt_tx_stop` уменьшился **592 → 64 B**, то есть на **528 B**. Цена — **+120 B text**. `.data`/`.bss`, публичный заголовок, размеры и выравнивание объектов TX не изменились.

Проверенная известная вложенная STOP-ветвь уменьшилась **3080 → 2552 B**. Даже её новый подытог превышает 2 KiB на **504 B**, ещё до кадра вызывающего приложения и прерываний. Это не доказательство полного максимального стека, времени работы, IRQ-safe поведения или размещения окончательной прошивки.

## Метод и воспроизводимость

1. Из `arm-closure-memory-root-r1/receipt.json` извлечены реальные флаги компиляции TX и упорядоченный список **25 индивидуальных** объектов линковки.
2. Старый и новый TX независимо скомпилированы в отдельные snapshots. Изменяются только путь snapshot/выхода и содержимое C кандидата; заголовок byte-identical.
3. Для обеих версий выполнен `ld -r` с теми же 24 неизменёнными исходными объектами и ровно одним соответствующим `13-mt_tx.o`. Готовый исходный aggregate не входит ни в один список линковки: двойного включения старого TX нет.
4. Старые TX object и aggregate совпали с оригиналом **побайтно**. Новый aggregate совпал с независимым полным root build.
5. Новый production recipe отдельно запущен без `--tx-stop` и с ним, сохраняя descriptor/memory overlays. Во всех 25 позициях совпали ожидаемые SHA-256 объектов и нормализованные `.su` функции/размеры/тип кадра. Совпали и оба aggregate.
6. Размеры/выравнивания/offsets TX проверены отдельными ARM object probes с прежним и новым header snapshot. Probe-объекты не включались в aggregate или ресурсные суммы.
7. Каждое звено выбранной STOP-цепочки подтверждено фактическим `BL` и `R_ARM_THM_CALL` в disassembly нового и старого aggregate. Выписки: `evidence-r3/selected_chain_direct_calls.json`.

Компилятор: `arm-none-eabi-gcc 14.2.1 20241119`, Cortex-M3, Thumb, soft float ABI, C11, `-Os`, freestanding, `-fno-common`, `-fno-short-enums`, function/data sections, `-fstack-usage`, строгие `-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Werror -pedantic-errors`. Полный argv сохранён в receipt и commands.log; флаги не воссозданы из предположений. Сравнены ELF/AEABI attributes: little-endian ELF32 ARM EABI5, ARMv7-M, Thumb-2, int-sized enums, 8-byte ABI alignment.

Указанные GCC, cc1, выбранный assembler, linker, nm, size, readelf, objdump и compiler headers привязаны к содержимому. `-print-prog-name=cc1/as` проверяет, что GCC действительно выбрал ожидаемые helpers. Shell wrapper запускает Python через `env -i`; дочерние команды получают только фиксированный PATH/locale/timezone/TMPDIR и запрет pycache. Финальный запуск выполнен при заданных снаружи ложных CPATH/C_INCLUDE_PATH/CPLUS_INCLUDE_PATH/OBJC_INCLUDE_PATH/GCC_EXEC_PREFIX/COMPILER_PATH/LIBRARY_PATH/DEPENDENCIES_OUTPUT/SUNPRO_DEPENDENCIES и PYTHONOPTIMIZE=2; они не попали в дочернюю среду. Контрольные проверки runner не основаны на отключаемом Python `assert`.

## Стек: только доказанная область

| Одновременно вложенный кадр | Старый, B | Новый, B |
|---|---:|---:|
| mt_runtime_step | 16 | 16 |
| mt_usb_cdc_step | 24 | 24 |
| mt_usb_cdc_step_impl | 40 | 40 |
| mt_control_rx_feed | 48 | 48 |
| mt_control_receive | 640 | 640 |
| mt_capture_link_stop | 1696 | 1696 |
| mt_tx_stop | 592 | 64 |
| append | 16 | 16 |
| memcpy | 8 | 8 |
| **Известная вложенная ветвь** | **3080** | **2552** |

Disassembly подтверждает собственные прологи: старый STOP сохраняет 36 B регистров и вычитает 556 B из SP; новый сохраняет те же 36 B и вычитает 28 B. Итог `.su` — соответственно 592 и64. Разность размера локальных массивов 544−12 сама по себе не заменяет измерение общего кадра; фактическая экономия —528 B.

`mt_tx_stop → append` остаётся обычным BL, затем append сохраняет16 B и вызывает memcpy через BL, который сохраняет ещё8 B. В новом STOP ACK/STATUS по-прежнему идут через append; эта вложенность сохраняется и после восстановления queued ABORT на месте. Остальные собственные кадры TX не меняются: read32/init/terminal0, append/shape16, hello/window_status32, enqueue24, poll96.

Не складываются последовательные decoder и dispatcher: `mt_stream_feed` возвращается до `mt_control_receive`. 2552 B — подтверждённая известная ветвь по исходникам и машинным вызовам, **не** полный максимум всей программы и **не** MCU watermark. Не включены вызывающий application/main, неизвестные callbacks/альтернативные пути, аппаратный exception frame, IRQ wrapper и дочерние ISR-вызовы, реальная вложенность NVIC/NMI/fault. Ограничения compiler output и текущей конфигурации сохраняются. 2 KiB по-прежнему заведомо недостаточно уже для этого подытога.

## Проверки безопасного выхода

До первого mkdir runner разрешает все входные файлы, проверяет hashes и защищает каждый реальный parent, входные roots, собственный Python-script directory и shell-wrapper directory. Выход обязан быть новым, не symlink и не пересекаться с защищёнными путями.

В r3 пройдены 11 отказных случаев: существующий выход; потомки base/candidate/toolchain; parent production recipe; существующий предок inputs; кандидат с `.c` symlink на внешний file-parent; symlink в родителе выходного пути; собственные script/wrapper directory; потомок исходного evidence; повторный собственный output. Во всех случаях ненужный выход не создаётся. Две положительные проверки `--check-paths-only` завершаются без создания выхода. Журналы сохранены как `recipe-guard-*`/`runner-guard-*`.

Никакие production/base/frozen USB005, host/**, remote, hardware или платные ресурсы не менялись. Все новые файлы этой проверки находятся только в `tx-stop-stack-arm/`. Поведение протокола и host regression проверяет отдельная работа; этот отчёт не подменяет её результатами ARM-компиляции.

## Повторный запуск

Из любой директории вызвать `runner/run.sh`, передав все пути явно. Выход должен быть свежим и располагаться вне всех защищённых входов и директории runner. Пример:

```sh
/workspace/shared/tx-stop-stack-arm/runner/run.sh \
  --baseline /workspace/shared/arm-closure-memory-root-r1 \
  --old-source /workspace/shared/usb-bridge-publication/base-checkout/firmware/transport/mt_tx.c \
  --candidate /workspace/shared/tx-stop-stack-draft \
  --recipe /workspace/shared/arm-closure-tx-stack-draft/tools/check_firmware_closure.py \
  --toolchain /workspace/shared/arm-resource-evidence/toolchain/root/usr \
  --input-root /workspace/shared \
  --out /workspace/shared/tx-stop-stack-arm/evidence-fresh
```

`--input-root` переносит полный набор зависимостей исходного receipt с сохранением относительной структуры; toolchain, candidate, baseline и recipe выбираются отдельными путями. Изменённый source/header/README/recipe требует новой явно проверенной привязки hashes, а не молчаливого принятия. Перенос на другую машину в этой проверке не выполнялся; portable path handling реализован, фактический запуск проверен в текущем окружении.
