# Программная связка native-контроллера и сеансовой записи

Черновой воспроизводитель для A `c4d4dc2966656b324518c8d0061811d1241870a3`
и B PR152 `7f632ae58883684d65d8f99d92571b5a67c644ff`, tree
`70a10d6dc5b568f794860776ee48c6ddbd69ce20`. Исходники обоих компонентов
не исправляются. Старый `tests/lv-collector-reproducer` закрепляет другую
пару и остаётся неизменным. Эта проверка не принимает GUI, протокол или MVP.

## Запуск

Нужны Linux, Python3.11+ и установленный GCC с ASan/UBSan. Установка пакетов,
сеть, Qt, USB и подключённая плата не нужны. Получить точные отдельные исходники
A и B. Входы проверяются по полному размеру и SHA256 потребляемых файлов из
`inputs.json`; имя папки само по себе ничего не доказывает.

```sh
python3 -I -B /absolute/A/tests/recording-session-reproducer/reproduce.py \
  --a-root /absolute/A \
  --host-root /absolute/B/host \
  --output /absolute/existing-parent/new-evidence
```

Пути абсолютные, нормализованные, без symlink; выход новый и вне входов.
По умолчанию используется `/usr/bin/gcc`; другой уже установленный компилятор
можно указать через `--cc`. Runner требует обычный Python, затем сам выполняет
probe обычным Python и с `-O` для каждой из двух C-сборок. Проверки не зависят
от `assert`. Каждый процесс ограничен 180 секундами; IPC — 5 секундами;
циклы pumping и ожидание writer barrier также ограничены.

## Проверяемая цепочка

Настоящие C controller, acquisition, capture-link, codec, command, session,
stream/RX и TX выполняются в отдельном native-процессе. Историческая fixture
используется только для синхронных callbacks аппаратуры и конечного TX sink;
её прежний `main` не запускается. `native_bridge.c` принимает фрагменты команд
через настоящий `mt_control_rx_feed`, без прямой передачи готовой команды в
controller. Сэмплы, продвижение TX и приём каждого префикса управляются явно.

A-owned `recorder_adapter.py` соединяет настоящие B `RecordingController`,
`AcquisitionRuntime`, `SessionSpool`. DeviceEmulator и B test helpers не
используются. Решения о Stop, владении результатом и новых ARM принимает
реальный controller; адаптер исполняет его intents и передаёт реальные events.

Порядок для полного окна:

1. Завершённое и проверенное END порождает необходимость Stop.
2. Отправляется STOP текущей generation; до matching STOP_ACK нет persistence.
3. После полного ACK разрешена запись. Хвост STATUS для этого не требуется.
4. Настоящий spool записывает и перечитывает данные; controller принимает
   точную durable receipt с привязкой к item/issuer/ordinal.
5. Тот же исходный объект подтверждается локально. RELEASE не отправляется.
6. Новый ARM допускается только после этого и пока запись не остановлена.

## Конечная матрица

По 13 сценариев в каждом сочетании C/Python:

- Auto и Normal по три разных окна, Single одно; команды передаются как
  префиксами до 64 байтов, так и по одному байту.
- В первом полном окне настоящий writer thread удерживается перед fsync.
  На основном потоке продолжается native/runtime polling; модельное время
  проходит 5400 мс. Нет receipt, локального ACK и нового ARM до освобождения
  writer. Исходный объект остаётся у runtime. Это модель задержки, не замер диска.
- Последний байт STOP_ACK временно удерживается: до него persistence запрещена,
  после него разрешена, хотя STATUS ещё не передан.
- Stop в ожидании crossing; после allocation до BEGIN; после BEGIN;
  после части DATA; после начала END. Уже принятые байты не отзываются.
  Stop-команда тоже фрагментируется; поэтому между нажатием Stop и её полным
  приёмом возможна передача дополнительных DATA. Это отражено в wire.
- Cached ARM отвергается после пользовательского Stop.
- Заведомо неверная receipt отвергается: исходное окно остаётся удержанным,
  ACK/RELEASE/новый ARM не появляются. Это ожидаемый отрицательный результат,
  spool сохраняется отдельно, завершённый archive не выдумывается.

Для full проверяются все 2048 исходных кодов. Для partial перечитываются ровно
сохранённые фрагменты и интервалы пропусков, без дополнения нулями. Для
no-BEGIN сохраняется abort event без искусственного массива. Matching Stop,
число ARM/Stop, отсутствие RELEASE, generation и outcome проверяются отдельно.
Свежий процесс открывает 12 завершённых архивов каждого варианта, сверяет
метаданные и SHA256/размер каждого member. Тринадцатый сценарий намеренно
оставляет незавершённый spool. Wire побайтно сравнивается между четырьмя
вариантами. Полные каталоги не объявляются одинаковыми: служебные receipt
содержат локальные пути и внутренние capability-объекты.

## Доказательства и ограничения

`receipt.json` хранит argv, версии/хеши, входы, коды возврата и статус.
`author-source/` сохраняет точные исходники текущего probe. В каждом сценарии
остаются native trace, host/device wire, API events с числом уже переданных
байтов, original spool, archive, ожидаемые поля и результат. Оpaque capability
в журнале обозначается строкой; реально проверяется identity объекта, а не
эта строка. stderr и неудачные запуски не удаляются.

Это cooperative filesystem workflow, не sandbox от враждебного компилятора
или одновременной подмены файлов. Не выполняются полный firmware runtime,
ADC driver, TinyUSB, физический USB, Windows GUI или реальная плата. Все
сэмплы окна имеют одно модельное время; Fs, settling и first-conversion этим
не измеряются. Software Stop не доказывает физическое прекращение сигнала.
Сеанс остаётся сегментным с неизвестными межоконными разрывами. Полный разряд,
непрерывная запись, power-loss durability и release readiness не подтверждены.

Авторские ошибки оснастки: r1 использовал ограниченный 20-pump handshake
чужого test Rig и не завершал handshake при одном байте; этот helper удалён.
r2 ошибся при JSON-представлении opaque receipt capability; исправлено только
журналирование. r3 и r4 прошли свои тогдашние матрицы. r5 неверно обращался к
полю `missing_ranges` вместо `partial.missing_ranges`; это ошибка probe,
не найденный дефект B. Журналы и доступные исходные снимки сохранены отдельно;
эти запуски не подменяют результат окончательной версии и независимое ревью.
