# Программная проверка collector LV-001 с текущим контроллером A

Это отдельный черновой воспроизводитель, не физический опыт и не приёмка
MVP. Старый tests/current-ab-reproducer не изменяется: там другая пара
исходников и Normal с продолжением через RELEASE.

Здесь закреплены A db09c263c022c27723fd9de9e4a79905097767c6
и B 76f9e41a12a69651ed39ce8fded31f0c0a25b471 (PR121).
Действующий r6 A a855ef341bb5eb8906a16af67f4d6b328f08f02f содержит те же
потребляемые байты. Сравнение выполняется по inputs.json, а не по названию папки.
Результаты общей приёмки другой пары исходников сюда автоматически не переносятся.

## Запуск

Нужны Linux, Python3.11+ и GCC с ASan/UBSan. Фактически использованы
Python3.12.14 и GCC14.2.0. Установка пакетов и сеть не нужны.
Предварительно получить отдельные точные исходники A и B из указанных commits.
Репозиторий приложения должен быть чистым; запуск не открывает serial/USB.

```sh
python3 -I -B "/absolute/probe/reproduce.py" \
  --a-root "/absolute/checkout-A" \
  --host-root "/absolute/checkout-B/host" \
  --output '/absolute/existing parent/new collector evidence'
```

Пути абсолютные, без symlink; выход новый, вне всех входных папок.
GCC по умолчанию /usr/bin/gcc; другой уже установленный GCC задаётся --cc.
Оригинальные файлы не исправляются и не нормализуются. Неподходящие байты
отклоняются до создания output. В отдельную папку копируются только15
закреплённых файлов A (семь пар C/H и историческая fixture) и восемь модулей B.
Это исключает случайный поиск других заголовков и Python-модулей из checkout.

## Что выполняется

- Компиляция настоящих controller/acquisition/codec/TX модулей A со строгими
  предупреждениями, затем отдельно ASan/UBSan; leak detection отключён.
- Отдельный тестовый bridge добавляет только LVWINDOW к существующей fixture.
  Он подаёт ровно2048 синтетических кодов; первый отсчёт выбирает реальный
  алгоритмический Auto timeout. Все отсчёты получают одно модельное время.
- Реальный LVCollector B выполняет один прогрев и20 основных попыток.
  Для каждой: ARM → окно → matching Stop ACK → модельная задержка диска5001мс
  с polling устройства → сохранение/повторное чтение → локальный consumer ACK.
  Следующий ARM всегда явный. Ожидается21 ARM,21 Stop и ноль RELEASE.
- Проверяются все исходные коды, числовые trigger/quality, generation/window,
  CAPS/config и CRC из END; MTCAP и sidecar перечитываются.
- Новый отдельный процесс вызывает verify_run и настоящий CLI B. Он должен
  сообщить sealed_unverified / RECOVERED_VERIFIED / prior_writer_outcome UNKNOWN.
  Это проверка целостности сейчас, не доказательство ACK прежнего процесса.
- Между compiler modes побайтно совпадают wire, native/transport traces и21
  MTCAP. UUID run_id различаются, поэтому весь каталог не объявляется одинаковым.

receipt.json хранит точные команды, версии/хеши, входы и результаты. Каждый
подпроцесс ограничен180секундами; при ошибке/таймауте сохраняются журналы,
группа процесса завершается. Существующий каталог не перезаписывается.
RUNNING или FAILED не являются успешным результатом. Принудительное завершение
всего процесса/потеря файловой системы может не оставить финальный receipt.

## Ограничения

Это синхронная аппаратная модель контроллера. Здесь не выполняются реальный
ADC driver, TinyUSB, полный runtime, Windows GUI и физическое измерение.
Время одинаково у всех отсчётов намеренно; оно не подтверждает Fs, first-conversion
или settling. origin=simulator; паспорт, напряжения и приборы остаются TBD.
Скрипт не является CLI запуска реального прибора. Входы доверенные, это не
sandbox для враждебного компилятора или файловой системы.

Авторская r1-проверка использовала фиксированные локальные пути и168 ранее
закреплённых файлов A. Этот r2 выделяет минимальные15+8 входов и переносимый
запуск; его собственный результат и независимое ревью нужны отдельно.
Предыдущие результаты/ошибки сохраняются; численная оценка здесь не назначается.
