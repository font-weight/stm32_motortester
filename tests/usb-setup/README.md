# USB-003: откат счётчика при отклонённом SETUP

Черновик [issue 55](https://github.com/font-weight/stm32_motortester/issues/55).
Автор реализации — Dot A; независимое ревью — Critic-A. Уровень проверки:
программа с настоящим TinyUSB core и моделью DCD. Аппаратная проверка не выполнена.

## Причина и граница исправления

В TinyUSB 0.21.0, commit `dae3f9a366bfcddbf9dcf1b48d7500286a849539`,
`dcd_event_handler` увеличивает `_usbd_queued_setup` до помещения события в очередь.
При заполненной очереди SETUP отклоняется, но увеличение остаётся. Поэтому после
опустошения очереди и нового настоящего BUS_RESET следующий GET_DESCRIPTOR может
быть пропущен: счётчик показывает несуществующий SETUP.

Патч откатывает только увеличение, соответствующее этому отклонённому SETUP.
Успешный путь, порядок increment → enqueue → hook и вытеснение более раннего
принятого SETUP более поздним не изменены. Обнуление счётчика при reset не добавлено:
после BUS_RESET в очереди уже может находиться настоящий новый SETUP.

Это ограниченная поправка учёта очереди: все проверенные вызовы producer и
consumer выполняются последовательно, без взаимного прерывания или вложенности.
Одна лишь сериализация producers между собой и нереентерабельность foreground
consumer этого не обеспечивают. Патч не добавляет критические секции и не
устраняет исходную гонку read/modify/write счётчика между ISR и foreground.
Реальные приоритеты/маршрутизация IRQ и защита общей транзакции ещё не реализованы.

Сам потерянный SETUP не становится безопасным: после его отклонения старый принятый
control request ещё может исполняться. Для прибора по-прежнему нужен fail-closed
барьер переполнения/эпохи, отбрасывание старых callbacks и запрет устаревших DCD
операций. USB-003 не закрывает эти требования USB-001/USB-002, не исправляет остальные
отрицательные примеры reset/submit/suspend и не доказывает восстановление устройства.

## Состав и контроль версий

Оригинальные vendored-файлы сохраняются без изменений. Патч и manifest находятся в
`firmware/third_party/usb/patches/`. `apply_setup_patch.py` принимает исходный
`usbd.c` и путь нового build-файла. Он проверяет SHA-256 входа, патча и результата,
применяет patch без fuzz и отказывается перезаписывать существующий файл.
Требуются Python 3 и GNU patch; загрузок или установки программ скрипт не выполняет.

- исходный `usbd.c`: `38de54351d81878e6543f2b022d0c39f45d28c8f0888491796398dec45e727be`
- патч: `51492cd96f4f9f8dd0699fe915f8c157c866f04cdc129e4c7c734e21f49b0f37`
- результат: `187144971b52e77385809500bd7401b46c3c332acda5f6221a1b45e440b8ddd0`

## Выполненные авторские проверки

`check_patch.py` принимает явные пути `--dependencies`, `--supporting`, `--firmware`,
`--toolchain`, `--output`; выходной каталог должен быть новым. Входы соответствуют
пакету USB-001: 35 upstream-файлов, supporting harness и firmware adapter. Скрипт
создаёт отдельную build-копию; исходные зависимости и harness не изменяет.
Выходной каталог должен находиться вне всех входных деревьев. После замечания
Critic-A добавлена проверка этого условия до создания каталога; восемь случаев
равного/вложенного пути отклонены без записи. Журнал:
`output-separation-checks.json`. Полная авторская матрица повторена после изменения.

Выполнены восемь существующих запусков: core и adapter, buffered и F1 dedicated
HWFIFO, обычный режим и ASan+UBSan. Во всех случаях exit 0. В adapter сохранены
14 групп проверок, включая реальные FIFO, частичные записи, Stop и явное
восстановление. Это программная модель USB-контроллера; MMIO не исполняется.
LeakSanitizer отключён из-за ограничений ptrace; проверки утечек не заявляются.

Отдельно выполнены три отрицательные проверки инструмента применения: неверный
исходник, изменённый патч, существующий выход. Все отклонены; вход не изменён.
ARM GCC 14.2.1 собрал изменённый core с `-std=gnu11 -Os -mcpu=cortex-m3 -mthumb`;
сохранены команды, символы, размеры, stack-usage и disassembly. SHA-256 объекта:
`da467c706a64bd3463194649346ce1ca4060f11e4cde4174fbb5e7b03be28d2d`.
В этой единице трансляции предупреждений компилятора не было. Это объект, не
полная ELF-прошивка, не оценка полного стека и не исполнение на STM32.

Финальные свидетельства автора: `evidence-author-final/commands.json`, `summary.json`, receipts
в `supporting/build*/`, `size.txt`, `nm.txt`, `objdump.txt`, `usbd.su`.
Upstream manifest внутри временной build-копии служит только происхождением:
после применения патча он не утверждает побайтовое равенство изменённого core.

Supporting-проверки содержат 14 новых сценариев и прежний core test в каждом
из двух режимов. Исправленный core прошёл 30 обычных и 30 ASan+UBSan запусков.
На оригинальном core в каждой матрице воспроизведены 16 ожидаемых отказов EP0;
остальные контрольные случаи прошли. Отдельный повтор автора с ASan+UBSan дал
30/30: `evidence-root-targeted/receipt.json`, полный вывод `root-targeted.log`.
Проверены серии из 1, 255, 256, 257, 511, 512, 513 и 1025 отклонённых SETUP,
принятое вытеснение, смешанные события и настоящие SETUP после queued BUS_RESET.
Кратные 256 отказы у исходной uint8-модели могут случайно скрыть дефект из-за
переполнения; это контрольные случаи, а не исправность исходного алгоритма.

Независимое заключение Critic-A и привязка к точному опубликованному commit
ещё ожидаются. Результат остаётся draft.
