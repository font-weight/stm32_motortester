# Наблюдение файлов исходников после сборки

Новый переносимый потребитель данных, 15 октября 2026 года. Третий кандидат
пока ожидает независимой повторной проверки. В первом независимый критик
выявил обход проверки PySide6 через namespace, незакреплённую идентичность
плана чтений, позднее появление pyvenv.cfg, отсутствие проверки после последнего
readback неполную проверку bootstrap-дескриптора и пропуск case-only имени выхода. Исходные байты/воспроизведения
сохранены; текущий кандидат закрывает причины и добавляет регрессии. Он не устанавливает пакеты, не выполняет
сборку, не запускает приложение и не доказывает происхождение bytecode.

## Назначение

Для каждого реально встроенного модуля PYZ сопоставить запись исходного
PYZ-00.toc с разрешённым исходным .py-файлом, прочитать его фактические байты
и создать совместимую с неизменённым companion таблицу source-inputs.json.
Не встроенные записи TOC перечисляются отдельно; их файлы не открываются.
Namespace даёт null. Имена пакетов согласуются с __init__.py.

Полный Windows-wrapper заранее допускает исходники приложения, установленную
среду, точные wheel-пакеты и наблюдаемую стандартную библиотеку. Он сохраняет
и закрепляет хеш manifest до вызова этого потребителя. Совпадающий хеш JSON,
переданный произвольным вызывающим, не является доказательством такого допуска.

Три корня передаются явно: app означает host-каталог точного приложения,
site — site-packages отдельной среды, stdlib — Lib доверенного интерпретатора.
Они не могут пересекаться. Manifest должен связывать именно эти корни, не
создавая новых разрешений. Его строгая схема определена в CONTRACT.md.

Приложение проверяется дополнительно: карта его .py-файлов должна совпасть
с фактическим закреплённым ZIP e263… . Site-источники сравниваются с картой,
ранее полученной wrapper из допущенных wheel-пакетов. Stdlib сравнивается с
наблюдаемым базовым снимком, без утверждения об официальной аттестации.
Потребитель не повторяет установку или распаковку всех wheel-пакетов.

## Последовательность и ограничения

- Проверяются точные тела PRELAUNCH r3, inspector, companion, pins и исходного ZIP.
- Подготовка исходного и изменённого initializer проверяется неизменённым companion.
- Из фактического EXE извлекаются только безопасно разобранные таблицы встроенного
  PYZ. Рабочий PYZ наблюдается отдельно и может отличаться; он не заменяет встроенный.
- Полный список источников проверяется лексически и по принадлежности manifest
  до открытия любого исходного файла. Неизвестный последний путь блокирует весь список.
- Проверяются реальные типы/размеры, предки, reparse/symlink, case aliases и разные
  пути к одному hardlink inode. Несколько имён модуля могут ссылаться на один и тот
  же канонический файл, но это не объявляется независимыми источниками.
- Идентичности и времена файлов из полного плана закрепляются до первого
  открытия; последующее чтение должно соответствовать этому снимку.
  Каждая фактическая .py-последовательность сравнивается с ожидаемыми размером/хешем.
  Единственное исключение — точный подготовленный PySide6/__init__.py для modified.
  Upstream RECORD не изменяется и не объявляется соответствующим изменённому файлу.
- Все входы полностью перечитываются. Их digest фиксируется до записи выходов;
  хеши выходных файлов связываются отдельно, без самоссылки.
- Оба выхода создаются только как новые файлы, затем читаются обратно; повторно
  проверяются входы, выходы и идентичности обычных каталогов-предков.
  Отсутствие pyvenv.cfg в проверенных stdlib-предках проверяется снова;
  финальная проверка выполняется после обоих последних readback.

Лимит фактических управляемых чтений/записей — 256 MiB, включая bootstrap,
перечитывания и выходы. До чтения исходников резервируется полный финальный
проход и максимальный объём записи/повторного чтения двух выходов.
Не более 8300 учтённых путей и 8192 уникальных исходных листьев; .py и каждый
JSON-выход до 2 MiB, EXE/work PYZ до 64 MiB. Это не лимит памяти или всей
операционной системы. Встроенный ZIP читается в памяти только после проверки
его точного известного хеша; кандидатный код не десериализуется и не исполняется.

## Вызов

CLI требует доверенный Windows CPython 3.13.16 и ключи -I -S -B.
Это проверка версии окружения процесса, не аттестация среды установки.
Все пути абсолютные, канонические; выходы отсутствуют, их родители существуют.
Поддерживаемое размещение EXE — trial/control/bundle/Motortester.exe или
trial/modified/bundle/Motortester.exe согласно variant; preparation — trial/preparation.
Таблица может записываться вне trial либо точно в trial/variant/source-inputs.json;
sidecar всегда вне trial. Все имена выходов проверяются на case-only коллизии
до чтения источников, перед записью и после финального readback.

    python -I -S -B source_inputs.py --prelaunch ABS_PRELAUNCH --inspector ABS_INSPECTOR --companion ABS_COMPANION --pins ABS_PINS --source-zip ABS_ZIP --preparation ABS_PREPARATION --pool-manifest ABS_POOL --pool-sha256 FROZEN_SHA --app ABS_HOST --site ABS_SITE --stdlib ABS_LIB --exe ABS_EXE --work-pyz ABS_ORIGINAL_WORK_PYZ --pure-toc ABS_ORIGINAL_PURE_TOC --variant control --source-output ABS_NEW_TABLE --sidecar-output ABS_NEW_SIDECAR

Для modified используется тот же закреплённый baseline manifest и точная
подготовка данного trial; только установленный initializer имеет разрешённое
изменение. Вариант не доказывает сам по себе, что EXE построен из этих исходников.
Оба результата затем проверяет отдельный PRELAUNCH и реальный wrapper.

## Результат

source-inputs.json содержит только требуемую companion карту имя → {bytes,sha256}
или null. Sidecar имеет статус UNCOMMITTED_SOURCE_OBSERVATION и сохраняет
проверенные связи, относительные пути, входные хеши и квалификации.
Успешный stdout SOURCE_BYTES_OBSERVED связывает оба размера/хеша и digest
входов, а также фактические счётчики I/O. Только успешный выход вместе с этой
квитанцией завершает наблюдение. Частично созданная пара файлов при отказе
сохраняется и не считается успехом; использовать новые имена при повторе.

source_pool_admission_verified, runtime_verified, wheel_bodies_verified,
build_execution_verified, source_to_bytecode_attestation, launch_authorized
всегда false. Реальные доказательства допуска среды и процесса — обязанность
полного wrapper. Никакой Windows/USB/аппаратной готовности эти файлы не дают.

## Переносимые тесты

Установить SOURCE_COLLECTOR_INPUT_ROOT и PRELAUNCH_INPUT_ROOT в корень
с сохранёнными prelaunch-rebuild-20261015, prelaunch-inputs-20261015,
app244b-sourcezip-20261015. Нужны точные тела из README PRELAUNCH.
Вызовы для обычного и оптимизированного режимов:

    python -I -S -B test_source_inputs.py
    python -I -S -B -O test_source_inputs.py

Тесты вызывают внутреннюю функцию на POSIX с непрозрачными синтетическими
EXE/DLL/PYZ и фактическими закреплёнными инструментами. Это не эксперимент
Windows и не обход production CLI для реального запуска приложения.

## Зависимость R4

Закреплены новые размер и SHA-256 PRELAUNCH после исправления последнего
readback. Интерфейс и смысл SOURCE-C1 не изменены; композиция требует
повторной проверки с этой точной зависимостью. Старый pin не принимается.

## Исправление R5: mtime между API

Дополнительная независимая проверка B выявила отсутствие сравнения mtime
между path-stat и handle-stat. Теперь сравнивается и mtime; несовместимая
Windows ctime по-прежнему сравнивается только внутри одного API. SOURCE
проверяет эту границу также при bootstrap. Добавлены отрицательные mtime
и положительные ctime-only регрессионные модели; Windows-опыт не заявляется.
