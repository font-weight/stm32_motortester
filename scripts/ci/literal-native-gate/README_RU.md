# Сверка метаданных и сохранение исходной квитанции

Черновой AUX-L1-L5-R6, 15 октября 2026 года. Это отдельная проверка данных,
которая не запускает приложение, DLL, native observer или сборку. Она не
подтверждает выполнение предшествующих Windows-проверок по одному полю PASS.
Полная обвязка и реальные испытания остаются отдельной незакрытой задачей.

## Что делает

1. Читает ограниченное исходное native-observation JSON как байты, ещё не
   разбирая содержимое. Сохраняет current.original.bin и current.identity.json
   в новом каталоге с проверкой обратного чтения. Пересериализации исходника нет.
2. Только после сохранения проверяет остальные файлы и закреплённые исходники
   помощников. Поздняя ошибка схемы, отсутствующий файл или неверный pin не
   должны уничтожить сохранённый оригинал и его длину/SHA-256.
3. Использует неизменённые pure-функции observer.bind_inputs, literal.bind и
   закреплённую функцию recording postcondition исходного workflow. Сопоставляет
   46 строк, TOC, manifest/provenance/archive, восемь checksum-имён, оригинальные
   smoke JSON и notice-sidecars. Карта 23 исходников app244b обязательна и
   независимо закреплена по проверенному исходному ZIP, а не только по взаимному
   совпадению утверждений двух квитанций.
4. Записывает UNCOMMITTED_AUXILIARY_METADATA в package-gate.json. Полностью
   перечитывает входы, проверяет выходы и финальную неизменность. Только код
   завершения 0 и stdout-квитанция data_only_joins_validated связывают результат
   с точным хешем файла отчёта. Сам отчёт не разрешает запуск чего-либо.

Флаги prior_package_execution_verified, native_comparison_verified,
actual_windows_execution, corresponding_source_verified, legal_clearance,
replacement_verified и launch_authorized всегда false. При отказе отдельный
failure.json/сообщение stderr различает полученный полный хеш исходных байтов
и завершённое сохранение копии. Частичный файл не объявляется оригиналом.
Выходы никогда не заменяются; частичные и непринятые файлы остаются для разбора.

Проверка исполняет только собственный доверенный код, стандартную библиотеку
и заранее проверенные по точным байтам Python-функции обработки данных.
Содержимое исходников приложения, native payload и произвольных receipt-полей
не исполняется. Эта программа не создаёт источник-производитель source-pool.

## Ограничения ресурсов

Один счётчик учитывает фактически прочитанные, записанные, повторно прочитанные
и отправленные в stdout/stderr байты. Лимит — 5 MiB; 16 KiB удерживаются для
сообщения об ошибке. Квитанция указывает managed_bytes, включая её собственные
terminal_bytes. Интерпретатор, его импорты и операции в памяти не выдаются за
управляемый файловый I/O.

Профиль: 18 входов и 8 зарезервированных выходов, 26 путей. Данный модуль
использует четыре выхода; native report/pipe capture/final composition здесь
не реализованы. Общий будущий набор с native helper — 118 уникальных путей,
поскольку семь общие. Native helper по-прежнему ограничен своими 99 путями и
123 MiB. Лимиты не относятся ко всей предшествующей сборке/архивной проверке.

Подробные caps — в CONTRACT.md и CAPS/OUTPUTS. В частности, current ≤128 KiB,
TOC ≤256 KiB, provenance ≤512 KiB. Общий observer допускает более широкий
диапазон; здесь он намеренно не поддерживается. Исходный run18 current имеет
69692 байта. Искусственная pretty-JSON версия в первоначальном тесте превысила
128 KiB и была корректно отвергнута; fixture переведён в compact UTF-8 без
увеличения cap. Исходные неудачные тестовые журналы сохранены отдельно.

Проверяются типы файлов, redirects/reparse, aliases, каталог-предки, identities
и сопоставимая mtime между path/handle API. Windows ctime сравнивается внутри
одного API. Это проверки ограниченного локального набора, не обещание защиты
от произвольной враждебной ФС или отсутствия изменений после последней проверки.
Внешний caller обязан отдельно ограничивать время процесса и сохранять логи.

## Запуск разработчиком

Использовать доверенный Python с -I -S -B. CLI получает runner-temp, run-id,
attempt, workflow-sha, workflow, literal, observer, baseline и reference.
Семь source/data входов берутся из точных проверенных версий, pins.json рядом
со скриптом неизменен. Сам launcher должен подтвердить Git-версию этого модуля;
самохеширование не является независимым доверием.

```sh
python3 -I -S -B literal_gate.py \
  --runner-temp ABS_TEMP --run-id RUN --attempt ATTEMPT --workflow-sha SHA40 \
  --workflow ABS_WORKFLOW --literal ABS_LITERAL --observer ABS_OBSERVER \
  --baseline ABS_BASELINE --reference ABS_REFERENCE
```

Фиксированные runtime paths относительно TEMP:
- native-observation-RUN-ATTEMPT.json и provenance-RUN-ATTEMPT.json
- native-notice-source-RUN-ATTEMPT.bin и native-notice-copy-RUN-ATTEMPT.bin
- motortester-RUN-ATTEMPT/pyinstaller/motortester/COLLECT-00.toc
- motortester-RUN-ATTEMPT/dist/Motortester/build-manifest.json
- motortester-RUN-ATTEMPT/archive-verification.json и SHA256SUMS.txt
- motortester-RUN-ATTEMPT/frozen-serial-import.json
- motortester-RUN-ATTEMPT/frozen-window.png.smoke.json
- motortester-RUN-ATTEMPT/frozen-recording.json

Новый выход: TEMP/literal46-RUN-ATTEMPT. Уже существующий каталог отвергается.
В будущей workflow-интеграции retention должен запускаться независимо от сбоя
предшествующего вывода логов (условие always). Эта интеграция пока не выполнена.
Отдельный Python-компонент не закрывает требование workflow автоматически.

## Воспроизведение переносимых тестов

Существующие проверенные входы доступны публично:
- Код prior helpers: commit 4ba680780879f0a91d52a4ab89bc9febf66f5243
- Метаданные/квитанции/notice bytes: data-only commit
  83bfcd271546649f289a085dc18b170781d390fa,
  https://github.com/font-weight/stm32_motortester/tree/83bfcd271546649f289a085dc18b170781d390fa

Последний snapshot содержит только данные и provenance-пояснения. Не сливать
его дерево в приложение. Он расширяет исходный B snapshot b65b3ca... с
неизменными четырьмя файлами. Это хеш-подтверждённое восстановление сериализаций
из публичного job log, не скачанный Actions artifact и не новый Windows-опыт.

Создать новый INPUTS с каталогами checkout и metadata. В checkout поместить
точный checkout указанного helper commit (без автоматического преобразования
концов строк); в metadata извлечь файлы data-only snapshot. Можно использовать
отдельные detached worktree либо git archive в новые каталоги. Нельзя заменять
пины похожими файлами из другой ветки. Затем:

```sh
LITERAL_GATE_INPUT_ROOT=ABS_INPUTS python3 -I -S -B test_literal_gate.py
LITERAL_GATE_INPUT_ROOT=ABS_INPUTS python3 -I -S -B -O test_literal_gate.py
```

Проверенное окружение автора — Linux x86_64/Python 3.12.14. У тестов есть
symlink-модель; возможность создавать ссылки обязательна. Тесты создают
синтетический TOC и явно синтетически согласованные metadata joins во временной
папке. Original run18 COLLECT-00.toc не восстановлен; его исторический SHA
83a8dcdc91d8c56a15d7b42365bfbd197c7001b7c59f41fbf335d0a60133dc37
не подменяется. Положительный тест не подтверждает исторический all-input join,
подлинность origin DLL, упаковку, права распространения или аппаратную готовность.

## Исправления R2

Независимая проверка R1 выявила неполные вложенные схемы и неверное сообщение
о сохранённом оригинале после повреждения копии. R1 получил REWORK 8.125/10;
его отчёт и неудачные проверки сохранены. Это не оценка R2.

В R2 добавлены строгие проверки вложенных данных, сопоставление EXE и счётчиков,
полное вычисление ожидаемого recording-summary из проверенной квитанции.
Чистые функции проверки recording перенесены без изменений из закреплённого
inspector; источники строк и хеши указаны в VENDORED_VALIDATORS.json. Проверяется
согласованность заявленных метаданных, а не факт реального запуска.

При ошибке сохранённые original/identity перечитываются только при достаточном
бюджете, не расходуя резерв 16 KiB. Если копию нельзя подтвердить,
retention_completed=false и retained_original=null; успешно полученный ранее
полный хеш входа остаётся в observed_original. Файл failure.json имеет статус
UNCOMMITTED_FAILURE_METADATA; итоговое stderr сообщает результат проверки
после его записи. Частичный файл не подтверждает сохранение.

Авторский набор R2 содержит 71 тест и дополнительные параметризованные
варианты; запускается отдельно в обычном и оптимизированном режиме. CLI-процессы
также получают -O при оптимизированном запуске. Независимый вердикт R2 требуется
отдельно. Полная Windows-обвязка, исходный TOC и испытания платы остаются открыты.

R3 также отвергает конфликт файла с родительским каталогом в manifest,
регистровый псевдоним build-manifest.json и превышение суммарного лимита
распакованного ZIP с учётом самого manifest. R2 сохранён отдельно; оценка R1
не переносится на R2/R3.

R4 исправляет повторно обнаруженный дефект: изменение или удаление оригинала
во время последнего чтения identity теперь выявляется завершающей проверкой
этой пары файлов. Изменение другого входа не отменяет подтверждение целой копии.
Файлы с несколькими жёсткими ссылками отвергаются, включая позднюю ссылку на
сохранённый оригинал. Оценки предыдущих ревизий на R4 не переносятся.

R5 также запрещает использовать обязательный файл build-manifest.json как
каталог. Требование единственной жёсткой ссылки является консервативным
ограничением профиля, не новым основанием для оценки прошлых версий.

R6 учитывает известный размер CPython notice в общей длине payload и
отвергает несовместимые сведения о размере/хеше одного объявленного origin.
Сведения об origin построенного EXE сопоставляются с самим EXE. Это только
проверка уже загруженных утверждений, новые origin-файлы не открываются.
