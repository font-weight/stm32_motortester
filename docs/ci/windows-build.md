# Проверка Windows-сборки, без публикации пакета

Текущая подготовленная проверка закреплена на PR130; точные SHA и границы — в последнем разделе. Черновая задача общей CI команды A. host/** и сама build_windows.py остаются
областью Dot B. Исторический источник предыдущих запусков — PR117
7bc2732358d855f0871ca4080d64db7b2b3a9979, tree
e083f317996d6b86f4286fe8c5758430291b6301, на родителе
e9df6f0adf64d9bbd177307abe0d47f73f14edb9. Это композиция текущего
приложения с serial import-only и ограниченным GUI screenshot smoke.
Recipe blob: 23dac801a223c05fd9fce9669f55e9d11c5cf287, SHA256
9898dcbfcce4845ea99d16f386ef653cbbfd50d73b884a4c0603165a7ceefbec.
Оба source pin и проверка recipe меняются согласованно.
Workflow хранит собственный SHA отдельно от SHA проверяемого приложения.

Запуск: pull_request в main только при изменении host-windows.yml или вручную
после доступности workflow_dispatch в основной ветке. Публикация draft PR с этим
файлом запускает проверку; это не слияние и не приёмка проекта. Время ограничено
30 минутами, права только contents:read, credentials не сохраняются. Сторонний
fork и приватный репозиторий исключены условием задачи.

GitHub API 10.10.2026 подтвердил public для font-weight/stm32_motortester.
[Правила GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
указывают бесплатные стандартные hosted runners для публичных репозиториев.
Поэтому используется только стандартный windows-2022. Larger/self-hosted runners,
платные ресурсы, секреты и изменение настроек учётной записи не применяются.

Artifact storage имеет отдельные квоты, свободный остаток аккаунта не проверен.
Поэтому workflow не использует upload-artifact, remote cache и публикацию release.
Диагностика build.log, frozen-serial-import.json, frozen-window.png.smoke.json,
manifest и SHA256SUMS
выводятся в журнал даже после ошибки сборки, если соответствующие файлы созданы.
Отсутствующие файлы обозначаются MISSING. По документации GitHub логи и job
summary не расходуют квоту artifact storage. ZIP остаётся только во временной
среде; отдельного разрешённого пути доставки пакета эта проверка не создаёт.

Изменение области относительно предыдущего workflow: байты синтетического PNG
теперь сохраняются в публичном job log как base64, если прочитанный снимок
не превышает 2 MiB. Размер, SHA256 и base64 относятся к одному ограниченному
снимку байтов; считывается не более 2 MiB + 1. Для большего файла содержимое
не выводится, ограничение указывается явно. Блок ограничен строками BEGIN/END,
base64 разбита на строки не длиннее 4096 символов. Это сохранение изображения
в логах, хотя upload-artifact не используется. Оно касается только демо,
созданного закреплённым кодом, без пользовательских фотографий и измерений.
Отсутствующий END, усечённый лог или несовпадение SHA256 не дают восстановленного
изображения. Частичный PNG после отказа является диагностикой, а не успешным smoke.

Точная обычная CPython3.13.16 x64, существующий hash-locked набор B, тесты, PyInstaller
и запуск полученного EXE выполняются неизменной build_windows.py. Сборка Windows
Server и синтетический снимок приложения не заменяют чистую Windows10, проверку
лицензий, настоящий USB, плату и независимый quality gate.

## Сохранение точных байтов checkout

Run38217032131 на PR117 остановился на source-тестах: 1091 тест, две ошибки
сравнения SHA256 и одна ошибка проверки лицензии. PyInstaller и оба реальных
frozen smoke не запускались; итоговых PNG/receipt/ZIP нет. Два опубликованных
несовпадения хешей точно воспроизводятся преобразованием LF → CRLF закреплённых
Git-исходников. Фактическое значение core.autocrlf и Windows-хеш notice не
выводились, поэтому эти детали не считаются измеренными.

Перед checkout в одноразовом hosted runner явно задаётся core.autocrlf=false.
После настройки Python каждый tracked-файл побайтно сравнивается с Git blob
точного HEAD; преобразования Git-фильтров при этом не применяются. Несовпадение
останавливает задачу до рецепта B. Это исправление среды CI, без изменения
исходников B, ожидаемых хешей, лицензий или тестов. Настройки компьютера
пользователя не меняются. Успех нового Windows run не предполагается заранее.

Область новой A-проверки объявлена до правок:
[PR34](https://github.com/font-weight/stm32_motortester/pull/34#issuecomment-6121497936).
После успешного неизменённого рецепта дополнительный read-only шаг:

- строго сверяет пять записей SHA256SUMS с фактическими файлами;
- проверяет CRC чтением всех ZIP-файлов, безопасные пути, отсутствие
  дубликатов, шифрования, symlink и посторонних корневых каталогов;
- сравнивает все файлы source.zip по raw Git blob с закреплённым host-деревом,
  а комментарий ZIP с source commit;
- сверяет весь бинарный архив с его manifest и точное совпадение встроенного
  и внешнего manifest;
- повторно применяет существующие строгие B-валидаторы smoke и проверяет,
  что manifest содержит те же результаты и сохраняет ограничения кандидата.

Архивы не извлекаются и дополнительно не исполняются. Границы чтения:
бинарный ZIP до200MiB, source ZIP до20MiB, PNG до2MiB, receipt/checksums до1MiB,
manifest до4MiB; внутри каждого архива до10000 записей, до1GiB суммарного
несжатого размера и до256MiB на запись. Превышение — явный отказ, не повод
удалить часть содержимого или молча повысить предел.

archive-verification.json пишет RUNNING до проверки и PASS только после
всех сравнений; ошибка сохраняет FAILED. Прерванный процесс может оставить
RUNNING, который не является результатом. Повторный шаг не перезаписывает
существующий receipt. Результат и хеши выводятся в прежнюю диагностику логов.
Авторский positive/control использовал одноразовый Git, фиктивный неисполняемый
EXE и старые run8 PNG/receipts исключительно как входные fixtures; это не новый
Windows-прогон. Повреждённое содержимое source ZIP с пересчитанными внешними
checksums отвергнуто, существующий receipt сохранён.

Этот шаг подтверждает только наблюдение архивов на runner. bytes_delivered=false:
ZIP по-прежнему не сохраняется и не передаётся пользователю. Отдельное разрешение
на временное хранение и проверка права/условий распространения ещё открыты.
Проверка хешей не подтверждает полноту лицензий, соответствующие исходники
зависимостей, ручную Windows10, физический USB/LV или приёмку релиза.
